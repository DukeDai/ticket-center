# DDD 领域模型 — 多源票券中心

> 配套文档：`SPEC.md`（业务合同）· `docs/schema-design.md`（物理模型）· `docs/connector-contract.md`（接入端口）
> 本文所有表名、字段名均与 `db/migrations/001_baseline.sql` 一一对应，可直接对照阅读。

---

## 1. 为什么这样切上下文

多源票券系统最容易犯的错，是把「源系统结构」直接泄漏进核心领域：
结果每个 GDS 都长出一套自己的商品表、自己的订单表，源一变全库跟着改。

本系统的切法是：**源是"上游系统"，不是"领域概念"**。

- 源系统的商品叫 `supplier_product`（源商品），我们的商品叫 `product`（规范商品）
- 源系统的订单不叫订单，叫 `booking`（向源预订）——它是**履约动作**，不是商业交易
- 源的原样报文永远关在 `supplier_raw_payload` 与 `supplier_product.raw_payload` 里，不外泄

商业上真正的「商品 / 价格 / 库存 / 订单 / 凭证」是我们自己的领域，与源数量无关。

## 3. 聚合与不变量边界

### 3.1 聚合清单

| 聚合根 | 成员实体 | 一致性边界 | 为什么这么切 |
|---|---|---|---|
| `product` | ticket_type, media, translation, 属性值 | 单商品内 | 商品属性是同一份真相，不该跨商品写 |
| `product_variant` | product_variant_option, product_variant_relation | 单变体内 | 一个可售组合的轴取值必须自洽；变体与源变体的覆盖关系独立于变体本身 |
| `product_variant`（组合态） | product_variant_relation（`relation_type='included'`）, supplier_variant_composition | 单组合内 | 组合的组件声明与源侧配方必须逐项对得上；两侧数量不一致就是「少给一份」或「多卖一份」，必须在写配方时就报出来 |
| `product_variant`（套装态） | supplier_variant_bundle, supplier_variant_bundle_part | 单套装内 | 套装是「源侧把整套当一个 SKU 卖」：它的成分声明与源侧整套报价必须对得上；形态还不许与配方态同时存在 —— 定价走哪条分支说不清，成本就会算两遍 |
| `supplier_product` | supplier_ticket_type, supplier_variant, supplier_session | 单源商品内 | 源侧对象树，保证源结构完整不被拆散 |
| `product_session` | product_session_source | 单场次内 | 一个场次的可供给源集合是原子的，改派要一致 |
| `channel_listing` | channel_listing_source | 单上架内 | 上架与货源绑定必须同时生效 |
| `sales_order` | sales_order_item, payment, refund | 单订单内 | 金额自洽必须在一个事务里保证 |
| `booking` | booking_attempt, booking_event | 单预订内 | 重试与状态流转独立于订单提交 |
| `voucher` | voucher_entitlement, redemption | 单券内 | 权益扣减必须原子，防超用 |
| `settlement_statement` | settlement_line | 单结算单内 | 汇总金额需自洽 |
| `inventory_hold` | —（引用渠道 / 场次 / 变体 / 源场次） | 单张预占内 | 「我们承诺出去多少」是一份账；它跨订单与购物车，靠行锁与幂等键保证不被重复占用 |

### 3.2 跨聚合引用一律用 ID + 快照

```sql
sales_order_item.detail_snapshot = {
  "title": "香港故宫文化馆 特展门票",
  "date": "2026-11-05",
  "slot": "10:00-12:00",
  "meeting_point": "特展入口 B2",
  "ticket_type": "成人票"
}
```

商品改名、改价、下架、源侧文案变更之后，历史订单详情必须原样可复现 —— 这靠快照，不靠 join 当前表。

### 3.3 为什么 Order 与 Booking 要拆成两个聚合

这是整个模型里最重要的一处决策。

| 维度 | Order | Booking |
|---|---|---|
| 一致性要求 | 强（金额、幂等） | 弱（可重试、可改派） |
| 失败语义 | 失败=业务失败，退款 | 失败=技术失败，换源重试 |
| 生命周期 | 秒级 | 分钟到小时级 |
| 跨系统边界 | 内部 | 外部（源 API） |

放一起的后果：源侧一次 3 秒超时，会把整个订单事务挂住，还会让「订单状态」和「源的状态」语义混淆。
拆开后：

- 订单提交只做本地事务 + 写 `event_outbox`，**不等待源**
- 预订失败 → `booking.failed` → 触发改派/退款/通知，**订单不受损**
- 源恢复后可通过 `booking.next_retry_at` 自动重报（DD 关心的「自动重报」）

## 4. 核心领域模型

### 4.1 归一化：三层结构

```
┌─ 规范层 (Catalog) ────────────────────────────────────┐
│ product          我们的商品：标题/描述/分类/地点/属性   │
│ ticket_type      我们的票种：成人/儿童/家庭            │
│ product_session  我们的场次：日期 + 时段               │
└────────────────────────────────────────────────────────┘
                         ▲  product_mapping
                         │  （多对多 + 置信度 + 证据）
┌─ 源层 (Supply) ───────────────────────────────────────┐
│ supplier_product      源商品（Ingresso 的 product、    │
│                       GlobalTix 的 package、票付通的   │
│                       goods —— 各叫各的）                │
│ supplier_ticket_type  源票种（item / spec / category）  │
│ supplier_session      源场次（departure / slot / 批次） │
│ supplier_price_calendar 源成本价                        │
└────────────────────────────────────────────────────────┘
```

**映射是多对多的**，原因：

- 一个源商品可能打包了多个我们的商品（源卖「双馆通票」，我们拆成两个 SKU）→ 允许 1 源 → N 规范商品
- 一个我们的商品可能由多个源供给 → N 源 → 1 规范商品

每个映射带 `match_type`（auto/rule/manual）、`confidence`（0~1）、`match_evidence`（判定依据 JSON），
支持「自动匹配先落 `pending_review`，人工确认后转 `active`」的审核流。

### 4.2 场次级冗余：多源不是只在商品级

只在商品级做多源不够 —— 源 A 有明天的场次，源 B 可能没有。
所以冗余下沉到**场次级**：

```
product_session (香港故宫, 2026-11-05, default)
   ├── product_session_source → globaltix  (role=primary,  priority=10)
   ├── product_session_source → jtb        (role=fallback, priority=20)
   └── product_session_source → 票付通     (role=fallback, priority=30)
```

下单前路由决策：`v_source_routing_candidates` 把
渠道 → 源 → 成本 → FX 归一 → 排序，一次查询给出首选与备选。

实测结果（C2C 渠道，香港故宫成人票 2026-11-05）：

| route_rank | 源 | 原币成本 | 折算 CNY | availability_mode |
|---|---|---|---|---|
| 1 | 票付通 | CNY 108.00 | **108.00** | push |
| 2 | globaltix | HKD 118.00 | 108.93 | live |
| 3 | goodfellows_jtb | HKD 125.00 | 115.39 | pull_sync |

注意：票付通虽然 `priority=30`（最靠后），但成本最低所以排第一。
**路由的排序键是「成本归一后的净值」，priority 只作同价时的 tiebreaker**。
如果业务上更看重稳定性而非最低价，改 `v_source_routing_candidates` 的 ORDER BY 即可，不用动数据。

### 4.3 变体：把「可售组合」从表结构里解出来

§4.1 的三层结构假设「一个商品 = 一个体验 × 若干票种」。环球影城打破了这个假设：
它卖的不是「一张成人票」，而是 **人群 × 票种 × 园区范围 × 加购件** 的组合。

#### 4.3.1 三步解法

```
product ──> product_variant ──> product_variant_option ──> product_axis_option
                │                                             (维度取值)
                ├──> product_variant_relation (可叠加：基础票 ← 快速通行证)
                │
supplier_product ──> supplier_variant ──> supplier_variant_mapping(coverage)
                                                │
                                                └──> product_variant
```

| 层次 | 表 | 职责 |
|---|---|---|
| 维度定义 | `product_axis` / `product_axis_option` | 哪些维度可变、每个维度有哪些取值（配置，不是 DDL） |
| 规范可售单元 | `product_variant` | 一个具体组合；**人群沿用 `ticket_type`，其余维度走轴** |
| 源可售单元 | `supplier_variant` | 源的 SKU（固定组合）或售卖方案（参数化） |
| 对齐 | `supplier_variant_mapping` | **覆盖**：源变体能满足哪些组合 |

#### 4.3.2 覆盖语义：源怎么跟变体对齐

两个源对同一商品的分解方式天然不同：

```
Trip.com：  TC-A1D-STD   成人 / 一日 / 单园区        ← 固定组合，精确命中
Zowoyoo：   ZWO-1D-BASE  人群∈{成人,儿童,老年} / 一日 / 单园区   ← 参数化，宽覆盖
```

所以映射不是一对一，而是**覆盖声明**：

```json
{
  "axes":     {"audience":["adult","child","senior"],
               "pass_type":["1d"],
               "park_scope":["studio_only"]},
  "excludes": []
}
```

判定规则（`fn_variant_covered`）：变体要求的每一项能力
（人群 + 各轴取值）都必须落在 `coverage.axes[axis]` 内，且不在 `excludes` 内。

这条规则是**「不能卖出履约不了的票」的技术保证**：
覆盖不全的源不会被路由选中，而不是先卖出去再在履约时失败。

#### 4.3.3 两个视图的分工

| 视图 | 粒度 | 用途 |
|---|---|---|
| `v_source_routing_candidates` | (商品, 票种) | 老商品的选源路径，保留不动 |
| `v_variant_routing_candidates` | (变体) | 新路径：强制做覆盖校验，覆盖不全的源直接不进候选 |

实测（北京环球影城，C2C 渠道）：

| 变体 | 首选源 | 备选 | 说明 |
|---|---|---|---|
| 成人·一日·单园区 | Zowoyoo ¥505 | Trip.com ¥545 | |
| 老年·一日·单园区 | **Trip.com ¥486** | Zowoyoo ¥505 | 同一商品，最优源与上面不同 |
| 儿童·一日·园区通票 | Zowoyoo ¥482 | — | Trip.com 没有儿童园区票，只有 1 个候选 |

而商品级视图对同一商品输出 **0 行** —— 两层结构表达不了这种商品。

#### 4.3.4 旧结构不是被推翻，而是被包含

「商品 × 票种」两层 = 只有人群一个轴的变体模型。迁移三步：

1. `(product, ticket_type)` → 生成一个 `base` 变体；
2. `supplier_ticket_type` → 生成一个源变体 + 1:1 精确覆盖映射；
3. 售价/成本价回填变体 id。

迁移后旧商品的变体路由结果与迁移前的商品级路由结果一致，
两套视图可以并存运行，直到调用方切换。

#### 4.3.5 有效期也是一条轴（2026-11-07 落地）

异构产品之间最容易被抹平的一条差异是**有效期**：源侧有两日票，
我们的规范场次是「(商品, 日期, 时段)」一行，两日票和单日票共用同一个场次。
如果出券写死「场次当天 + 1 天」，卖了两日票发出来的券只管一天 ——
客户第二天拿着付过钱的票到门口，闸机判 expired（钱收了、票买了、门不认）。

所以有效期不是常量，是**轴选项上的一个事实**：

```sql
product_axis_option.valid_days   -- 1d → 1，2d → 2；NULL = 这条轴不描述有效期
```

| 层次 | 承载 |
|---|---|
| 轴选项 | 这条取值有效几天（`valid_days`） |
| 变体 | 挂了哪些轴取值 → 有效几天 = `COALESCE(MAX(valid_days), 1)` |
| 凭证 | `valid_from = 场次当天`，`valid_to = 场次当天 + 有效天数` |
| 差异对照 | `v_variant_comparison.valid_days` + `v_variant_validity` 的窗口 |

**为什么取最大值而不是求和**：有效期是「窗口有多长」，不是「各条轴各占几天」。
一个变体同时挂了两个不同的天数，那是不变量 73 要报出来的歧义，不是这里该猜的东西。

**为什么放在轴上而不是商品或变体上**：轴选项本来就是「产品的差异维度」的载体。
放在别处会与轴打架 —— 同一个事实两处写，迟早分叉。
放在 `option_attrs`（自由 jsonb）里也不行：它要被计算、要被门禁断言，
得有自己的类型和约束。而且种子里原本就把它塞在 `option_attrs` 里，
**没有任何函数读它** —— 事实存在但没人用，等于没有。

源侧能不能兑现这个窗口是选源时定的：`coverage` 里必须含对应的取值
（`fn_variant_covered`）。卖了之后这条不许变（不变量 75）——
真变了走退款，不是把历史订单改成「当时就不该卖」。

#### 4.3.6 组合：异构融合的第二个方向（2026-11-07 落地）

前面 4.3.2 的覆盖语义解决的是**方向 A**：一个源 SKU 覆盖多个可售单元
（源侧一张「成人 / 儿童通用」通票，我们拆成成人票与儿童票）。

但真实商品还有**方向 B**：一个可售单元由多个源 SKU 按数量组成。
GlobalTix 的官方示例就是一个家庭套餐：

```
mappingId: 80041201-8004120101|2 + 80041201-8004120102|2 + 80041902-8004190201|1 + 80041902-8004190202|1
           成人门票×2            + 成人快速通行证×2     + 儿童门票×1            + 儿童快速通行证×1
```

这个套餐在源侧是一个 SKU，在我们侧必须能表达成「四个组件、各几个」。

| 侧 | 承载 | 语义 |
|---|---|---|
| 规范侧 | `product_variant`（`variant_role='combo'`）+ `product_variant_relation`（`relation_type='included'`）+ `quantity` | 这个可售单元由哪些组件组成、各几个 |
| 源侧 | `supplier_variant_composition`（`product_variant_id` / `component_variant_id` / `supplier_variant_id` / `quantity`） | 这个源 SKU 顶的是哪个组件、几个 |

**为什么两侧都要有声明**：只有规范侧 = 源侧少给一份（客人少拿一张票）；
只有源侧 = 我们多卖一份（公司多赔一张票）。两侧逐项对得上才有意义
（不变量 79、80）。

**为什么 `component_variant_id` 要显式记**：两个组件数量一样、又被同一个源 SKU
覆盖得住的时候，「这个源 SKU 顶的是哪个组件」只能靠猜。猜就是瞎猜，
所以配对关系落到列上，对账逐行比。

**组合的要求集合 = 组件要求的并集**（`fn_variant_requirements`，递归 CTE）。
所以单个源 SKU 覆盖不住整张配方（组合的要求比任何单张票大），
而整张配方（各成分覆盖的并集）覆盖得住 —— 方向 A 与方向 B 不打架。

**组件只许一层**：组件要是组合，两侧的对账就得递归算，错了没人说得清。
触发器 `fn_guard_included_relation` 当场挡住嵌套。

**组合不许直接挂源映射**（触发器 `fn_guard_combo_mapping` + 不变量 81）：
组合的成本 = Σ 组件成本 × 数量，一次预订要带整组源 SKU。
若允许组合直接挂一条源映射，定价函数会用**一个**源 SKU 的成本
给整张套餐定价 —— 收三个人的钱，出一张票。宁可少卖，不可卖错。

#### 4.3.7 组合的售卖：计价单位与履约单位分开（2026-11-07 落地，2026-11-08 修订预订单位）

模型到「两侧对得上」为止时，组合还卖不了。这一节是把它接到成交上的那部分。

**为什么分两个单位**：

| 单位 | 承载 | 一个套餐有几个 |
|---|---|---|
| 计价单位 | `sales_order_item` | 1（一份套餐一个价） |
| 履约单位 | `sales_order_item_source` | N（一个成分一行） |

组合有多个成分、一个成分可能有多张票，所以履约事实必须挂在成分上：
出券、票额、持票人都指得到「这一份是成人还是儿童」。
**普通明细也写一行**（`component_variant_id` = 明细自己的变体），
所以两条路只有一套代码 —— 不为组合单开一套平行实现。

**但预订的单位不是成分，是源 SKU**（2026-11-08 修订）。
参数化源里成人票与儿童票是**同一个源 SKU**（人群是购买时选的一档），
按成分建预订就是同一个源 SKU 订了两次：
源侧看到两张订单单，我们这边一条客户订单对两个源单号，对账对不上；
源侧只确认了其中一个成分时，整张套餐是半成品 —— 收了三个人的钱出了两张票。

所以有三个单位，不是两个：

| 单位 | 承载 | 一个套餐有几个 |
|---|---|---|
| 计价单位 | `sales_order_item` | 1（一份套餐一个价） |
| 履约单位 | `sales_order_item_source` | N（一个成分一行） |
| 预订单位 | `booking` | M（一个源 SKU 一条，M ≤ N） |

预订覆盖哪些成分由 `fn_booking_components` **推**出来
（按「明细 + 源 SKU + 源场次」），不另存一列 ——
推导是唯一的，一个成分只属于一个源 SKU 分组，不会分叉。
出券时再按成分把票码和持票人分下去（各发各的张数、各按各的持票人与有效期）。

**成分的源 SKU 取自配方，不重新选源**（`fn_combo_components`）。
重新选源意味着配方只是装饰：按 A 源的价格卖、按 B 源出票，
客诉说不清、对账对不上 —— 这跟硬约束 15 是同一个道理。

**不可售就明确不可售**（`v_combo_price_gap` 逐条列原因）：
成分缺价 / 成分不在同一场次 / 成分来自不同的源 / 价格被锁 / 按团报价。
少卖好过卖错。

**持票人归属靠 `item_index`，不靠猜**：同一个成分变体出现在多行明细里时，
光看 `variant_id` 分不出持票人属于哪一行。带 `item_index` 的实名必须全带
（一半带一半不带就报错 —— 部分归属的实名会把票发错人）。

**超卖按源场次总需求判**：多个成分可能落在同一个源场次上，
逐个成分判会卖超（每个成分都看到「还剩 2 张」，合起来卖了 4 张）。
所以先按源场次汇总这一单的总需求判一次，再逐成分判可售数。

**接不上的情况要说清楚**：源侧把整套套餐当**一个** SKU 卖的情况，
从 `coverage` 看不出来 —— 看不出一个源 SKU 是「一整套」还是「一张谁都能用的票」，
猜错就是「按 A 源的价格卖、按 B 源出票」。
所以这种形态**单独声明**（§4.3.9 套装），不推断、不猜。

#### 4.3.8 组合在 C 端：配方自己推自己的日历（2026-11-08 落地）

组合是**我们自己的配方** —— 源侧没有它的商品条目，目录同步作业看不见它。
所以 §9 那条「源侧同步 → 读模型」的路径对它不成立：
源侧同步跑得再勤，组合在 C 端也是一片空白。

组合要上 C 端，得自己长出日历。`fn_sync_combo_calendar()` 做两件事：

- **售价行**：取成分在同一天、同一源场次上的售价行，凑齐全部成分才算当天可售；
  金额走定价函数的组合分支（成本 = Σ 成分单价 × 份数），同步作业不另算一遍钱。
- **日历格子**：`price_calendar`（基准行）× `channel_listing`（上架），
  格子上的价格取自刚推出来的价格行。

推出来的价格行 `cost_source_product_id = NULL` —— 组合的成本来自配方，
不是来自某一个源商品。所以「采纳成本必须可追溯到具体源」这条对组合改口径：
有**有效的源侧配方**即算可追溯。

**有效期终点 = 成分窗口的并集**（最长的那个）：

| 配方 | 成分窗口 | 组合给客户的窗口 |
|---|---|---|
| 2 × 一日成人 + 1 × 一日儿童 | 1 / 1 | 1 天 |
| 2 × 两日成人 + 1 × 一日儿童 | 2 / 1 | **2 天** |

不是最短（第二天进不去），不是相加（多赔客户一天）。
不变量 89 的两边**独立读**：组合那边走 `fn_variant_validity_days`，
成分那边直接读 `product_axis_option.valid_days` ——
拿自己证明自己永远绿灯。

**人群不选标签，带编码。** 组合不带一个「家庭」标签，
带的是每个成分的**人群编码 + 份数 + 各自的天数**。
「2 成人 + 1 儿童」这句话由前端按 locale 拼 ——
展示文案不进模型（硬约束 9）。

**构成进读模型**（`c_variant_composition` / `v_c_variant_composition`）：
请求链路不许 join 主数据去算份数。与主数据分叉由不变量 90 当场抓住；
挂着的组合必须卖得掉（不变量 91：格子要有价格）。

**跨币种的组合：没有单一源币种。** 成分可能各自是不同币种
（源侧日元、我们卖人民币），所以组合售价行的顶层 `fx_rate` / `fx_as_of` 是空的 ——
那是「这里没有单一的值」，不是「同币种、汇率 1」。
逐成分的留痕在 `price_calendar.rule->'combo'` 里：
同币种 → 因子 1、快照日期为空；跨币种 → 必须有快照日期且因子能独立复算。
这条路径要自己的门禁（不变量 92）——
组合的 `cost_source_product_id` 是空的，不变量 45 按那个字段 join 源价行，
直接跳过组合，没人复查就等于留了个假快照日期都没人知道。

#### 4.3.9 套装：源侧把整套当一个 SKU 卖（2026-11-09 落地）

异构融合到这一步有三种形态：

| 方向 | 语义 | 模型 |
|---|---|---|
| A | 一个源 SKU 覆盖多个可售单元 | `supplier_variant_mapping.coverage` |
| B（配方） | 一个可售单元由多个源 SKU 按数量组成 | `supplier_variant_composition` |
| B（套装） | **一个源 SKU 把整套当一个 SKU 卖** | `supplier_variant_bundle` |

第三种从 `coverage` 看不出来：一个源 SKU 覆盖住整个可售单元，
可能是「一整套」，也可能是「一张谁都能用的票」。
两者都能覆盖住，差别全在语义上 —— 成本、预订单位、库存池、有效期都不一样。
**看不出来就不能猜**，所以套装单独声明（`supplier_variant_bundle` +
`supplier_variant_bundle_part`），触发器挡住它同时又是配方态。

**三个单位不许混**：售卖单位是**套**（订单明细的份数）、
成分单位是**预订的单位**（一个源 SKU 一条预订）、
入场份数是**发的券的张数**。一套「2 成人 + 1 儿童」= 1 套 / 3 份入场。
不变量 99 守着这条：入场份数 = 套装声明的份数 × 套餐份数。

**成本来自源侧那个整套报价**，不是成分单价相加，**也不重新路由**。
分摊到成分只是为了对账（不变量 98：Σ 分摊 × 套数精确等于整套成本 × 套数）。

**库存扣源侧整套票种的池子**，不是每个成分各扣各的：
预占一条，份数是套数。

池子的取数有两条口径（020 补上的）：

- **余量不许跨源票种相加。** 查套装池子时，可售数只能来自**这个源票种自己的快照**；
  源侧没报它就是**不知道**，不许拿同一场次里别的票种的余量顶上
  （不变量 100）。用儿童票的库存卖整套票，卖出去的钱收不回。
- **需求按池子加总。** 落单时预占按池子汇总这一单里所有套装的套数再比余量
  （不变量 101）。逐明细各算各的看不见超卖：两条明细各记着「还剩 1 套」，
  各要 1 套，各自都过，合起来就是 2 套。

「不知道」时不拦单（返回 0 意味着「卖完了」，会让整个商品下架，比超卖更贵），
但要把当时的可售数写进明细快照，事后对账用。

**有效期是源侧声明的**（`supplier_variant_bundle.valid_days`），
必须盖住成分窗口的并集（不变量 97）—— 盖不住就是第二天进不去。

**缺口要说清**（`v_bundle_gap`）：没有源侧报价 / 没有规范场次 / 没绑源场次 /
没有源侧票种 / 有效期盖不住 / 可售数未知。看不出来就说看不出来。

#### 4.3.10 三种形态放在一起看（2026-11-09 落地）

上面三种形态各有读法，但**没有一个视图能把它们放在一起看**。
根子在选源：`v_variant_routing_candidates` 与 `v_variant_source_coverage`
都走 `fn_route_candidates`，而它只建模方向 A ——
**配方与套装的可售单元在那些视图里一行都没有**。

不是它们不卖，是读侧看不见它们在卖。看不见的后果不是少一行，是看不懂：
同一个商品下两个几乎一样的家庭套餐（配方 ¥1656.48 / 套装 ¥1740.00）
交付同样的内容，哪个在卖、卖不卖得掉、差在哪，运营侧一个都答不上来。

`v_variant_supply_forms` 一行一个「可售单元 × 一天 × 一个渠道 × 一种形态」。
三条口径：

- **形态不许消失**（不变量 102）。声明了就必须在对照视图里出现 ——
  少了 = 那一路供给在运营侧是隐形的，而它还在真实地卖。
- **成本取定价函数那个**（不变量 103）。单张形态取 `route_rank = 1` 的候选，
  不是各源里的最小值：选源按基准币种排序，最小值按本行币种排，
  渠道币种不是基准币种时这两个「最小」不是同一个源。
- **份数只写一份**（不变量 104）。入场份数来自 `fn_variant_composition`
  （与 C 端构成读模型同一个来源），对照视图不重数。

形态整体的缺口只在这个形态**真的卖不掉**时才报；逐源的缺口放在候选明细里。
混在一起就是「✓ 能供，却说当天没报价」—— 自相矛盾的话比没有话更坏。

#### 4.3.11 源 SKU 下架时形态不许缩小（2026-11-10 落地）

上面三条口径有一个前提：**成分行存在**。
而成分解析时写的是 `JOIN supplier_variant ... AND status = 'active'` ——
源侧把某个 SKU 下架时，那一行直接消失。

从聚合的角度看，这是一个**外部事实侵入聚合内部结构**的经典问题：
`supplier_variant.status` 是源侧的事实，它本该影响「这个成分有没有价」，
不该影响「这个成分算不算存在」。写成 JOIN 之后，源侧的一次下架
就把聚合内部的成分集合改小了 —— 配方于是静悄悄地变成了一个更小的套餐。

两个后果：

- **配方**：少一个成分就按剩下的成分重新定价（收 3 份入场的钱，出 1 份票），
  而 C 端构成读模型还写着 2 个成分 / 3 份入场 —— 读侧与写侧分叉。
- **套装**：整套的成分全没了，形态行从对照视图里消失 ——
  不是「卖不掉」，是「看不见」。

`fn_price_variant` 的 `n_priced = n_parts` 门禁本该挡住，但门禁看到的是
**已经缩小的集合**：2 个成分里 2 个都有价，`n_priced = n_parts` 通过。
门禁守的是「配齐了没有」，这里的问题是「集合本身就少了」。

改法只有一处语义：**源的可用性从「决定这一行在不在」改成「决定这一行有没有价」**。
成分行改用左连接源 SKU；源下架时这一行还在，只是没有报价。
改完不需要另写一套判定 —— `n_priced = n_parts` 这条现成的门禁就把残缺的套餐挡住。

三条口径：

- **成分不许消失**（不变量 105）。声明过的成分解析后还是那些行，一个不少。
- **少了价的成分 = 整个形态卖不掉**（不变量 106 / 107）。
  配方与套装分别守：源下架时形态不许还能卖 —— 对照视图说不可售，
  定价函数也不给价。只守一边的话，运营看到一个「能供」的形态就敢上架，
  或者收银台按一个已经配不齐的套餐收钱。
- **形态不许从对照视图里消失**（不变量 102）。单张 / 配方 / 套装都一样：
  源下架时形态行仍然在，`can_fulfil = false`，缺口点名「源 SKU 已下架」。

两条不许：

- **残缺的套餐不许报成本。** 成分缺一个时 `cost_in_target` 留空 ——
  残缺套餐的钱不是这个套餐的钱。
- **源侧下架是事实，我们改不了源侧。** 不许为了留住事实去改写历史订单，
  也不许拿「源下架了」当借口把套餐缩小着卖。宁可少卖，不可卖错。

### 5.1 Order

```
                    └────┬─────┘
                         ▼
               ┌──────────────────┐
               │ awaiting_payment │
               └────┬────────┬────┘

                    ▼        ▼
              ┌──────────┐  ┌──────┐
              │ expired  │  │ paid │

                               │ 启动 saga
                               ▼
                     ┌──────────────────┐
                     │ booking_pending  │
                     └──┬───────────┬───┘
              booking  │           │  booking

                        ▼           ▼
                 ┌───────────┐  ┌────────┐
                 │ confirmed │  │ failed │
                 └─────┬─────┘  └───┬────┘
                       │ 部分出票      │
                       ▼              │
              ┌──────────────────┐   │

                 └───────────┘       │
                                      │
   paid / booking_pending / confirmed │ partially_fulfilled / fulfilled / failed
                                      │        （RefundRequested）
                                      ▼
                              ┌────────────┐
                              │ refunding  │──退款失败──> 回到退款前的状态

                                    ▼
                              ┌──────────┐
                              │ refunded │
                              └──────────┘
```

退款入口有六条边（从六个可退状态都能进 `refunding`），
出口有七条（`refunded` 加上六条「退款失败退回原状态」）。
这张图是 `state_transition` 表的读法，不是另一份定义 ——
改流转只能改表，改了表这张图会跟着不对。


### 5.2 Booking

```
 pending ──发起──> requested ──源确认──> confirmed ──出票──> ticketed
    ▲                  │
    │ 可重试错误        │ 不可重试错误 / 业务拒绝
    │ (timeout,5xx)    ▼
    └────── next_retry_at   failed
                            │
                            ├──> cancelled（用户取消 / 超时未付）
                            └──> expired（源侧超时未支付）
```

`booking_attempt` 逐次记录请求/响应/耗时/错误分类，`booking_event` 逐次记录状态流转。
两者共同支撑「这个单为什么失败」的客服自助排查。

### 5.3 Voucher

```
 pending ──出票──> issued ──核销──> used
    │                │
    │                └──> expired（过有效期）
    └──> void（源侧作废）
 issued/used ──退款──> refunded
```

两条边的写路径各归一处：`issued` 由出券写（`fn_issue_voucher`，§5.6），
`used` 由核销写（`fn_redeem_voucher`，§5.8）。谁也不越界改别人的状态。

### 5.4 状态机住在库里（2026-11-06 落地）

上面三张图不是文档摆设：合法流转写在 `state_transition` 表里（唯一来源），
两个触发器把它变成机制。

| 触发器 | 时机 | 做什么 |
|---|---|---|
| `fn_guard_state_transition` | BEFORE UPDATE | 目标状态不在合法边上就报错 —— 状态改不动 |
| `fn_emit_state_event` | AFTER INSERT / UPDATE | 状态一变就往 `event_outbox` 写一条领域事件 |

放在库里而不是 Go 里，有三个理由：

- **谁都绕不过去。** Go、psql、脚本、手工改库，走的是同一条路。
  放在应用层只挡得住走应用层的写入。
- **状态与事件不会分家。** 事件是状态变化的副产品，不是调用方的额外责任。
- **不用改代码就能改状态机。** 加一条合法流转 = 往 `state_transition` 插一行
  + 同步 `SPEC.md` §5，不需要发版。

代价：表里那套流转得有人维护，写错了会挡住业务。所以它同时是不变量 46-49 的对象 ——
「状态必须能从初始状态走到」保证表里的边至少自洽（不会有一条孤立的边让人永远走不到）。

### 5.5 下单写路径（2026-11-07 落地）

订单聚合的写入口只有一个：库里的 `fn_place_order()`。它不是一个「存一下」的函数，
而是把几条领域规则收在一处：

| 规则 | 落在哪 | 领域含义 |
|---|---|---|
| 幂等键必填 | `idempotency_record` + `ON CONFLICT DO NOTHING` | 同一个意图只能产生一张单 |
| 金额与采纳源只取 `fn_price_variant` | `fn_place_order` 内部调用 | 价与源是同一个决策的两面 |
| 一单一币种 | `fn_place_order` | 币种是行级字段，混币种加总无意义 |
| 明细走快照 | `detail_snapshot` / `pricing_snapshot` | 订单历史不依赖当前商品表 |
| 实名按 `checkout_requirement` 收 | `fn_place_order` 校验 + `order_holder` 落库 | 要哪些字段是商品/票种决定的，不是下单方决定的 |

**为什么下单不建预订。** Order 与 Booking 拆成两个聚合（见 §3.3），
预订在支付成功之后才由 saga 创建。下单阶段源侧可能超时、可能报错 ——
把这些塞进下单事务，源侧的抖动就会变成订单聚合的失败。
所以下单只落订单聚合，`created → awaiting_payment` 之后的事交给编排。

**为什么幂等在库里而不是应用层。** 幂等键可能来自三个地方：C 端重试、B 端重复提交、
定时任务重跑。它们可能落在不同进程上。应用层缓存挡不住跨进程，
库里的唯一索引 + 事务能挡住。

### 5.6 履约写路径（2026-11-07 落地）

支付 → 预订 → 出券的写入口各只有一个，全在 `db/migrations/005_fulfillment.sql`：
`fn_record_payment` / `fn_create_bookings` / `fn_request_booking` /
`fn_record_booking_attempt` / `fn_complete_booking` / `fn_issue_voucher` /
`fn_retry_booking` / `fn_apply_order_fulfillment`。

Booking 聚合（§3.3）在这里接手 Order 交给它的活：把「要出票」变成「票出了」。

| 规则 | 落在哪 | 领域含义 |
|---|---|---|
| 支付金额必须等于订单应付 | `fn_record_payment` | 收了多少钱是事实，不是调用方说了算 |
| 幂等按渠道流水 | `fn_record_payment` + `ux_payment_provider_txn` | 同一笔渠道回调重放多次是常态，不是异常 |
| 重复收款当场报错 | `fn_record_payment`（`006` 守卫） | 收了两笔钱只能有一笔入账，另一笔要走退款 |
| 预订的源场次来自绑定 | `fn_create_bookings` 读 `product_session_source` | 场次是绑定的，不是按日期猜的 |
| 确认预订必须带源侧预订号 | `fn_complete_booking` | 没有它就无法回头找源对账 |
| 票码与持票人一一对应 | `fn_issue_voucher` | 券发给谁、几张，是票务事实 |
| 票码不许是券号派生的 | `fn_issue_voucher`（`016`） | 券号是连号的、猜得到；票码是闸机认的东西，猜得到等于没有闸机 |
| 订单履约状态只由一套推导 | `fn_apply_order_fulfillment` | 状态是结论，结论只有一个算法 |

**为什么预订的源场次不能按日期猜。** 同一个商品在不同源的场次编号体系不同
（携程的场次 id、GlobalTix 的 session id、票付通的自有编号），
按日期对齐的猜法在「同一天两个场次」「场次改名」时会悄悄选错源 ——
表现就是「按 A 源的价格卖、按 B 源出票」。场次级绑定（`product_session_source`）
是唯一的对应关系来源，不变量 59 守它。

**为什么履约状态不归调用方写。** `fulfillment_status` 是从明细出票情况数出来的结论。
让调用方填这个字段，等于让每个人各自实现一遍数法 ——
订单显示「已履约」但票只有一张、或者显示「待出票」但票早就出了，都是这么来的。
不变量 60 把结论和事实钉在一起。

**为什么预订与出券不是一个函数。** 源侧的预订确认和票码到达**不是同一时刻**：
有的源先确认再给票码，有的源一次给全。合成一个函数，就得为「源先确认、票后到」
造一个假状态。所以 `fn_complete_booking` 接受「确认了但暂时没有票码」，
出券是独立的第二步。

### 5.7 退款写路径（2026-11-07 落地）

退款的写入口只有一个，全在 `db/migrations/007_refund.sql`：
`fn_request_refund` / `fn_approve_refund` / `fn_complete_refund`。

Refund 在这里是什么聚合？**它不是 Order 的一部分** ——
它是「一次退钱这个动作」的记录，跨在 Order 与 Payment 之间。
Order 拥有「这张单现在什么状态」，Refund 拥有「退过没有、退了多少」。

| 规则 | 落在哪 | 领域含义 |
|---|---|---|
| 退款作用域是整单 | `fn_request_refund` | 按行退需要摊分口径，那是业务决策不是工程决策 |
| 退款金额必须等于订单实付 | `fn_request_refund` | 少退客户投诉，多退公司承担 |
| 有没有收到钱看支付记录 | `fn_request_refund` 查 `sales_payment` | 订单状态是人写的，支付记录是事实 |
| 幂等键必填，同键异内容报错 | `fn_request_refund` | 重放一次退款就是多退一次钱 |
| 发起即进 `refunding` | `fn_request_refund` | 免得一边退一边出票 |
| 失败退回去 | `fn_complete_refund` + `previous_order_status` | 退款失败不是订单完了，订单要能接着走 |
| 退成功事实一起改 | `fn_complete_refund` | 退了钱，明细/凭证/预订/支付/订单必须一起变 |
| 票已核销不许整单退 | `fn_request_refund` | 票用掉了该不该退是业务判断，不是函数判断 |
| 必须先放行才能落结果 | `fn_complete_refund`（`016`） | 放行是必经之路；放行人留痕（`approved_by`） |

**为什么退款不是订单状态机的一条边。** 订单状态机（§5.1）描述的是
「这张单走到哪一步了」。退款是**对这张单做的一次动作**，可能失败、可能重试、
可能有多笔（退了一部分再退剩下的）。把它压成订单状态机上的一条边，
就没有地方记「退过两笔、第一次退失败了、第二次是谁批的」。
所以 Refund 是独立记录，订单状态只是它推出来的结果。

**为什么失败时订单要退回去。** 退款失败的常见原因是渠道超时 ——
钱可能退成功了，只是我们没收到回执。这时候订单还挂在 `refunding`，
客服看到的就是一张「卡住的单」，既不能发货也不能告诉客户「已退款」。
记下 `previous_order_status` 并在失败时恢复，订单才能回到
「已支付、等待重试」这个真实状态。退不回去的状态就留在 `refunding`，
配 `RAISE NOTICE` 提示人处理 —— 不硬改成某个看起来对的态。

**为什么退成功要一次改完事实。** 退款是唯一一件「钱的状态」和「票的状态」
必须同时动的事。只改订单状态，下一秒对账就会发现：
订单说已退款、支付记录说成功、明细说已确认。三方口径不一致，
每一笔都要人工去查。系统宁可当场多写几行 UPDATE，也不留下这种分叉。

### 5.8 核销写路径（2026-11-07 落地）

核销的写入口只有一个，全在 `db/migrations/008_redemption.sql`：`fn_redeem_voucher`。

Voucher 聚合（§5.3）在这里接手 Booking 交给它的活：把「票发了」变成「票用了」。
核销不是 Order 的一部分 —— 它是**一次扫票这个动作**的记录，
跟 Refund（§5.7）一样是独立记录，券的状态是它推出来的结果。

| 规则 | 落在哪 | 领域含义 |
|---|---|---|
| 核销记录永远追加 | `voucher_redemption` 每扫一次插一行 | 重复扫票是事实，不是噪声 |
| 一张券最多成功核销一次 | 唯一索引 `ux_redemption_single_success` | 重复入场是票务欺诈的入口，机制要挡住 |
| 额度一次用尽 | `voucher_entitlement.consumed_quantity` | 一人一券消耗 1，整团一券消耗整团人数 |
| 不认核销但留记录写清原因 | `voucher_redemption.reason` | 「为什么进不去」是闸机和客服都要看到的事实 |
| 订单在退款不认核销 | `fn_redeem_voucher` 读订单快照 | 钱在退的时候把人放进去，退款就退不干净 |
| 票码撞车不猜 | 按闸机所属的源收窄候选集 | 猜错就是「拿 A 源的票进了 B 源的场」 |
| 过期只落记录不改券状态 | `fn_redeem_voucher` | 券状态留给过期作业统一改（作业未做），一件事归一件事 |

**为什么核销不写幂等键。** 前面三段写路径（§5.5 / §5.6 / §5.7）都写了幂等键，
核销刻意不写 —— 因为**核销记录必须每次都追加**。
幂等键的语义是「同一个意图重复提交，返回同一笔」，用在核销上等于把第二次扫票压掉。
核销要压的不是记录，是**状态**：一张券只能成功核销一次。
这件事由券的状态 + 唯一索引兜底，不由幂等键兜底。

**为什么重复扫码要留痕。** 重复扫票有两类来源：网络重试丢了响应（无恶意），
和同一张票被人扫了两次（可能是有意倒票）。
系统分不清这两者 —— 也不需要分清。**两种都是事实，都要留**。
如果核销记录只留成功的那一次，事后对账就看不出「这张票今天被扫过几次」，
票务欺诈的入口也就看不见了。所以第二次扫记 `result='duplicate'`，
并带回第一次成功核销的记录 id 与时间，调用方据此对账。

**为什么额度一次用尽。** 凭证是**一次性入场凭证** —— 一张券就是一次入场。
一人一券的券一次扫一张（消耗 1），按团报价的整团一券一次扫全团（消耗整团人数）。
核销成功后券从 `issued` 变 `used`，额度不再可用。
多次入场的通票还没进这套模型 —— 真要支持，额度就不该被一次扫票用尽，
这一条要重新设计，不是加个开关。

**为什么退款和核销互相挡。** 两个方向都要挡：
订单在 `refunding` 时不认核销（钱在退的时候把人放进去，退款就退不干净）；
票已核销时不允许整单退款（票已经用掉了，钱该不该全退是业务判断，不是函数判断）。

### 5.9 库存预占写路径（2026-11-07 落地）

可售数的写入口只有一个，全在 `db/migrations/009_inventory_hold.sql`：
`fn_available_qty` / `fn_reserve_qty` / `fn_hold_inventory` / `fn_release_hold` / `fn_expire_holds`。

`inventory_hold` 是一份**承诺账**：它记录「我们说了要占多少、后来卖出没有、现在放没放」。
这份账横跨购物车与订单，所以它不是 Order 聚合的成员 —— 它有自己的状态与幂等键。

| 规则 | 落在哪 | 领域含义 |
|---|---|---|
| 可售数只有一个实现 | `fn_available_qty` | 「还剩多少」只有一份算法，两份算法必然分叉 |
| 源侧快照与我们的承诺对账 | `unreflected = GREATEST(our_sold − source_sold, 0)` | 源侧 `sold` 只含已同步的销量；不区分就会每同步一次少卖一半 |
| 不知道就是不知道 | `known = false`（不是 0） | 0 意味着「卖完了」，会让整个商品下架，比超卖更贵 |
| 并发靠锁不靠先查后改 | `fn_reserve_qty` 按源场次升序 `FOR UPDATE` | 先查后改在并发下会让两个订单各卖各的最后一张 |
| 明知不够当场报错 | `fn_reserve_qty` 抛「库存不足」 | 源侧说了只剩 3 张还要 5 张，不能靠运气 |
| 预占是事实、幂等键必填 | `fn_hold_inventory` 的 `hold_no` | 重放一次预占等于凭空多占一份 |
| 订单关上放掉承诺 | 触发器 `trg_release_holds_on_order_close` | 谁改的订单状态都一样放掉；`voided` ≠ `released`，卖出过的事实不许改写 |

**为什么 `voided` 与 `released` 必须分开。**
`released` 是「占过，但从没卖出」；`voided` 是「卖出过，后来又被收回（退款 / 取消 / 超时）」。
合成一个状态的话，退款与超卖的账永远算不清 ——
「卖出去过」和「从没卖过」在账上分不开，对账时那 18 张和那 2 张就说不清了。

**为什么可售数要在锁内算。**
`fn_reserve_qty` 先按 `supplier_session.id` **升序**加行锁，再算可售、再判断。
升序是为了不让两个订单互相死锁（A 锁 1 再锁 2、B 锁 2 再锁 1）。
锁外先查后改是最常见的超卖写法：两个并发请求都读到「还剩 1 张」，各卖 1 张。

**为什么「不知道」时不拦。**
源侧没给库存数据时，我们并不知道有没有超卖风险。
拦住等于全站停卖（源侧库存同步没跑起来的时候），
不拦等于可能超卖。**这里选不拦，但把当时看到的数写进明细快照**
（`detail_snapshot.availability`）—— 超卖发生后，事后能算出我们多卖了多少、
对谁多卖的。这是「不知道」时唯一诚实的做法。

所以核销这边**刻意不锁订单行** —— 退款路径的加锁顺序是「订单 → 凭证」，
反向加锁会死锁。核销读一次订单快照判断即可，
真撞上了退款路径会要求人工处理，两边不可能同时放行。

### 5.10 改派写路径（2026-11-11 落地）

改派是 Order 聚合里的一次**重下明细**：一条明细跟当前的世界对不上了，
把它按今天的世界重新下一次（换个源、重新定价）。

写入口只有一个：`fn_reassign_order_item(order_id, order_item_id, reason)`
（`db/migrations/024_reassign_order_item.sql`）。

| 规则 | 落在哪 | 领域含义 |
|---|---|---|
| 改派 = 重新选源 + 重新定价 | 源与价都取自 `fn_price_variant` | 选源与定价同源：改派换到的就是当前世界选出来的那个源 |
| 只发生在未收款时 | 订单状态 + 有无成功支付记录 | 已成交的金额失去依据，差价退不退是业务决策，这类单走退款 |
| 只对没预订、没出票的明细 | 函数内当场报错 | 发到源侧的预订是事实，不能靠换源抹掉 |
| 只对单张形态 | `product_variant.variant_role` | 配方与套装的源是**声明**的，换源要重新声明，不是改派 |
| 成分行与预占跟着源走 | `sales_order_item_source` + `inventory_hold` | 履约按成分行建预订；预占记的是「我们承诺了多少」。不改 = 按 A 源的价格卖、按 B 源出票 |
| 留痕写自己的，不改写历史的 | `detail_snapshot->'reassignments'` | 下单时的定价快照是冻结的，它记的是当时报给客户的那个价 |

**为什么成分行与预占必须跟着走。**
一个明细的源写在三处：明细本身、成分行（履约真正用的源）、库存预占（占哪个源侧池子）。
只改第一处，另外两处还记着旧源 —— 前者造成「按 A 源的价格卖、按 B 源出票」，
后者造成「按新源卖、按旧源占库存」。两者的后果都是客诉说不清、对账对不上。

**为什么改派写自己的留痕。**
改派不是把历史改掉，是记下「发生过一次改派」。留痕追加在
`detail_snapshot->'reassignments'`，每一跳记「从哪个源哪个价、到哪个源哪个价」。
下单时的定价快照保持冻结 —— 它是「当时报给客户的那个价」的事实。

**为什么已收款的单不许改派。**
改派重算的是钱。钱已经收了，重算出来的数与收的那笔对不上，
差价退不退是业务决策（行级退款还没落地）。系统不自己编这条规则，
所以这里明确报错，让它走退款流程。

## 6. 领域事件与 Outbox

```
聚合内状态变更 ──> 同事务写 event_outbox ──> 发布器轮询 ──> MQ / 订阅方
```

`event_outbox` 与业务写在**同一事务**里，因此不会出现「订单确认了但事件丢了，通知没发」。

写入 outbox 这一步**不是调用方的责任**：触发器 `fn_emit_state_event` 在状态变化时
自动落事件（见 §5.4）。事件名写在 `state_transition.event_type` 里，
所以「哪些状态变化会产生哪些事件」只有一份来源。


通知侧另有 `notification_outbox`，其 `channels` 字段是一个 JSON 数组，记录
每个通道（短信/Lark/邮件）各自的状态，支持**单通道失败不影响其他通道**并独立重试。

## 7. 值对象与领域服务

| 概念 | 落地方式 |
|---|---|
| 金额 | `NUMERIC(12,2)`，不用浮点；多币种由行级 `currency` 决定 |
| 时间 | 源侧本地时间存 `supplier_session.local_start_label` + `timezone`；统一时刻用 `timestamptz` |
| 币种换算 | `fx_rate` 快照（按 `as_of_date` 取最新），**不允许实时汇率**，保证成本可比与可复现 |
| 归一化指纹 | `product.canonical_key`（标题+地点+品类+时长的稳定哈希），自动聚类的锚 |
| 变体指纹 | `product_variant.variant_key`（人群 + 各轴取值的稳定拼接），去重与外部引用的锚 |
| 变体覆盖判定 | 领域服务 `fn_variant_covered(coverage, variant_id)`：源变体的覆盖声明是否完整覆盖规范变体的全部能力；`fn_variant_coverage_gaps` 给出缺口 |
| 计价基准 | `sales_order_item.pricing_basis`：`per_person`（总价 = 单价 × 份数）/ `per_group`（总价 = 团总价，与人数不成正比，团总价真值在明细快照 `group_total`）。`quantity` 始终是人数，实名与预占都依赖它 |
| 价格保护 | `supplier_variant.is_price_locked`（源侧是否受保护）+ `price_calendar.price_locked`（平台侧派生）。**锁价随采纳源变化**：同一变体改由非保护源供货即解锁 |
| 路由决策 | 领域服务，输入 (channel, product, date, ticket_type)，输出有序候选源列表 |
| 对客定价 | 领域服务 `fn_price_variant(variant_id, date, context_channel_id, price_channel_id)`：**唯一实现**（SQL 函数）。采纳源 → 成本（快照汇率折算）→ 售价（成本加价 / 最低毛利 / 下限三者取大）→ 划线价 → 折扣。生效 `min_margin` = 渠道要求与源侧底线取严；锁价行与按团报价行豁免（源方定价，平台无权加价）。`fn_reprice_rows()` 是重算入口 |

## 8. 已知取舍

| 取舍 | 选择 | 代价 | 何时该改 |
|---|---|---|---|
| 源商品拆成多个规范商品 | 允许（映射多对多） | 运营复杂度高 | 实际遇到打包拆分再开启审核流 |
| 库存 | 实时查 + 快照 + 缓存三层 | 三处数据可能打架，靠 `captured_at`/`expires_at` 判新旧 | 若源普遍不支持实时查，可砍掉 `availability_cache` |
| 售价 | 与源成本**分表** | 两表 join 才能看全貌 | 若只需要展示价，可合并 |
| 定价实现位置 | 住在数据库（SQL 函数） | 不能在应用层里复刻一份；调试要会写 SQL | 若将来引入分布式事务或独立定价服务，再评估外移 |
| 售价行的性质 | 金额列是**派生物**（由定价函数填） | 库里存了派生值，必须靠不变量 41 保证不与规则分叉 | 若改成事件溯源重算历史售价，可去掉冗余列 |
| 选源与定价的关系 | **同源**：候选集与排序键只有一份（`fn_route_candidates`），路由视图与定价函数都从它取 | 分叉的后果是「按 A 源的价格卖、按 B 源出票」；不变量 43 守住这条 | 若将来引入按实时库存/健康度动态改派，需要把动态因素也并进 `fn_route_candidates` 的排序键，而不是另开一条路 |
| 汇率留痕 | 快照（`as_of_date ≤ price_date` 的最新一条），留痕日期取两腿较晚的那一天 | 留痕日期能独立复算出同一个因子（不变量 45）；同币种不折算就不留快照 | 若基准币种变更，历史留痕按当时的基准币种解释，不回溯重算 |
| 事件 | Outbox 模式（polling） | 有延迟 | 若吞吐要求高，可换 CDC |
| 商品 ID | `BIGINT IDENTITY` | 单库自增，跨库合并麻烦 | 若要多机房写入，改 UUID |
| 订单表 | 未分区 | 数据量大后清理困难 | 单表超 2000 万行时按 `placed_at` RANGE 分区（注意分区表的唯一约束须含分区键） |
| 维度建模 | 通用轴（`product_axis`）+ 按需实例化变体 | 变体行数随维度组合增长；运营要理解"轴/取值/变体"三层 | 若某些品类维度极多（如酒店房型），可把该维度的取值直接挂到 `product_variant.variant_key` 上跳过轴表 |
| 人群维度 | 沿用 `ticket_type` 而非新建轴 | 人群与"票种"两个概念容易混淆 | 若将来"学生票/军人票"等人群细分超过三层，再独立成轴 |
| 源对齐 | 覆盖语义（非一对一） | 一个源变体可对应多个规范变体，映射表比一对一大 | 若某源永远 1:1，`is_exact=true` 即可，不影响判定 |
| 异构融合的方向 | 三条形态都建模：方向 A（一个源 SKU 覆盖多个可售单元）+ 方向 B（一个可售单元由多个源 SKU 按数量组成）+ 套装（一个源 SKU 把整套当一个 SKU 卖）；都已接到成交，配方与套装都已走到 C 端 | 套装从 `coverage` 看不出来，所以只能单独声明（`supplier_variant_bundle`），不许推断 | 若将来源侧自己给出「整套」标识，接进 `supplier_variant_bundle` 的声明表，别去猜 `coverage` |
| 组合的 C 端呈现 | **人群编码 + 份数 + 各自的天数**，不选「家庭」这类标签 | 标签要 locale 才能渲染，模型里放标签就得维护多语言；份数与天数是语言无关的事实 | 若将来要按人群筛选，把编码做成可筛维度，不把标签塞进模型 |
| 组合的有效期 | 成分窗口的**并集**（最长的那个） | 取最短就是第二天进不去，取相和多赔客户一天；并集对应「一次入园，套餐里最长的那张票说了算」 | 若源侧支持「多日票分段使用」，要另设计分段窗口模型 |
| 组合的折算留痕 | **逐成分留**，顶层留空 | 组合没有单一源币种，顶层填 1 等于声称「没折算过」，对账会去查一份不存在的折算 | 若将来要求组合整体用一个币种结算，才允许顶层有值 |
| 预订的单位 | **源 SKU**（一个源 SKU 一条预订），成分由 `fn_booking_components` 推出来 | 配方态的整张套餐的原子性取决于源侧能力；套装态是一条预订顶整套（预订单位 = 套） | 若源侧把整套拆成多条预订，套装的预订单位口径要跟着改 |
| 组合的组件深度 | 只许一层，不许嵌套 | 组合套组合表达不了 | 若真出现套组合，需要重新设计对账口径（递归 + 基数） |
| 变体级路由与商品级路由并存 | 两套视图并存，老商品走老路径 | 两套逻辑要同步维护 | 调用方全部切到变体级后，下线 `v_source_routing_candidates` |
| 下单写路径的位置 | **住在数据库**（`fn_place_order`），Go 侧只拼参数收结果 | 应用层不能改业务规则，改规则要发迁移 | 若将来下单要跨库、要独立部署，才评估外移 |
| 幂等键的存放 | 库里的 `idempotency_record`（唯一索引 + 事务） | 键要占库空间，且清理策略要另定 | 键表变大时按时间分片归档 |

## 9. C 端：为什么单独有一层读模型

供给侧模型解决的是「怎么把源接进来」，C 端模型解决的是「怎么把它展示出去、卖出去」。
两者的建模逻辑不同，不能用同一套表硬扛：

| | 供给侧模型 | C 端读模型 |
|---|---|---|
| 优化目标 | **准**（忠于源结构） | **快**（列表页扇出） |
| 数据形态 | 规范化、一份真相 | 反范式、可重建 |
| 新鲜度 | 各源各异 | 整卡同一次刷新 |
| 失败后果 | 算错成本 | 卡片与详情页对不上 |

读模型（`c_product_card` / `c_product_calendar` / `c_variant_facts` / `c_variant_calendar`）
由后台作业从主数据 + 价格 + 库存物化而来，
**主数据永远是唯一真相，读模型随时可重建**。
漂移检测见 `v_c_readmodel_drift`。

**差异也是读模型的一部分（2026-11-07 落地）。** 供给侧模型把异构差异表达在轴上
（`product_axis` / `product_axis_option.valid_days` / `supplier_variant_mapping.coverage`），
但 C 端请求链路不许 join 主数据 —— 于是差异必须被物化进读模型：
`c_variant_facts` 带人群 / 轴取值 / 有效天数 / 退款口径，
`c_variant_calendar.valid_to` 带有效期终点。

物化时**不重算**：每个字段都从 `v_variant_comparison` 取。
物化之后**不许与主数据分叉**（不变量 76 逐字段比对），
物化之外**不许另算有效期**（不变量 77 保证日历终点 = 格子日期 + 有效天数）。

这不是「C 端特有的展示逻辑」，而是**供给侧模型的一个投影**：
差异住在供给侧，读模型只是它的一个切面。
把差异留在供给侧而让 C 端自己算，就是第二份实现 ——
分叉的后果是「展示说两日票、发出来的是一天有效期的券」。

C 端展示内容（亮点/包含/须知/评价）与购买漏斗（购物车/优惠券/实名/预占）的完整说明，
见 `docs/c-end-model.md`。
