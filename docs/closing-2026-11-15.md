## 2. 做成了什么

### 2.1 交易的每一段都有唯一实现

这是整个项目最核心的一条：**同一件事只有一处实现**。

| 段 | 唯一实现 | 迁移 |
|---|---|---|
| 下单 | `fn_place_order` | `004` |
| 履约 | `fn_record_payment` / `fn_create_bookings` / `fn_request_booking` / `fn_record_booking_attempt` / `fn_complete_booking` / `fn_issue_voucher` / `fn_retry_booking` / `fn_apply_order_fulfillment` | `005` / `006` |
| 退款 | `fn_request_refund` / `fn_approve_refund` / `fn_complete_refund` | `007` |
| 核销 | `fn_redeem_voucher` | `008` |

Go 侧只拼参数、只读结果。它不重算金额、不重排源、不自己算状态、
不自己判退款资格、不自己判能不能进场。

这件事不是风格偏好。**两份实现的后果是「按 A 源的价格卖、按 B 源出票」** ——
客诉说不清、对账对不上、佣金算不出。

### 2.2 异构融合的三种形态都走到了成交

多源票券真正难的地方不是接几个 API，是**让结构完全不同的源长在同一套模型上**。
这里认了三种形态，每种都有各自的声明方式（**不靠猜**）：

- **方向 A**（一个源 SKU 覆盖多个可售单元）：`supplier_variant_mapping.coverage`
- **方向 B**（一个可售单元由多个源 SKU 按数量组成）：`supplier_variant_mapping` 之外另立 `supplier_variant_composition`
- **套装**（源侧把整套当一个 SKU 卖）：`supplier_variant_bundle` + `supplier_variant_bundle_part`

三者并排对照在 `v_variant_supply_forms`（一行一个「可售单元 × 一天 × 一个渠道 × 一种形态」）。

### 2.3 差异没有在归一化时被抹平

有效期、有效范围、可退性、人群 —— 这些是异构产品之间最容易被抹平的差异。
抹平的后果很具体：**卖了两日票发出来的券只管一天**，客户第二天到门口闸机判 expired
（钱收了、票买了、门不认）。

现在有效期长度是轴选项上的**数据**（`product_axis_option.valid_days`），
唯一读法是 `fn_variant_validity_days`，出券只调它。
两日票与单日票在 C 端日历上**长得不一样**。

### 2.4 「约定」被逐条换成「机制」

这是 2026-11-13 到 11-15 那批提交的主线。每一条都是「原来靠自觉，现在靠机制挡住」。

| 原来 | 现在 |
|---|---|
| 「记得调 `store.Quote` 转义」 | `store.NewSQL(...).Bind(v)` + `internal/sqllint` 扫 AST 门禁 |
| 「改状态机记得同步 SPEC」 | `state_transition` 表是唯一来源 + 守卫触发器 + 事件触发器 |
| 「机器不许洗掉人的判断」 | `internal/writelint` 规则 1（判断表上的 upsert 不许无条件覆盖） |
| 「源标识写之前要校验」 | `internal/writelint` 规则 2（写源侧表的包必须校验标识不为空） |
| 「预占 TTL 默认 900 秒」 | 归一在函数体里（`COALESCE(p_ttl_seconds, 900)`），不是调用方 |
| 「作业要有人跑」 | `tc-connect jobs` 唯一入口，间隔交给 cron |
| 「文档里的条数要准」 | `make counts` 数一次，文档只引用不抄 |
| 「公开接口要校验渠道」 | `requireChannel` 一个闸门，渠道不存在与不对外服务给同一个答复 |

门禁挂在 `make check` 与 CI 上。**门禁绿着而 bug 还在比漏报更坏**，
所以每条门禁都做过反向验证（把实现改坏，确认门禁真的变红）。

### 2.5 读侧不重算事实

C 端读模型与 B 端运营读模型都是**读模型**，请求链路里不 join 主数据、不重算。
两份实现一旦分叉，运营看到的与真下单的就不是一回事 —— 清单不可信。

具体到商品详情页：**售价行是「对外报的价」，不是成交价**（成交价在订单明细快照里）。
两者不一致是正常的，拿一个去对另一个的账就对不上。
有效期同理，详情页带的是轴选项上**声明**的天数，唯一读法仍是 `fn_variant_validity_days`。

## 3. 还差什么

按「能不能开工」分三档。

### 3.1 差外部文档与凭证（等别人的）

| 事项 | 卡在哪 | 找谁 |
|---|---|---|
| Trip.com 分销侧凭证（`aid` / `sid` / `key`） | 拿到就能跑沙箱 + 生产分层测试，核对 4 个待确认点 | 商务 |
| GlobalTix 接口文档 | 端点与请求体进 `configs/api_config.json` 后启用适配器 | 商务 |
| 其余五源文档（Ingresso / JTB / Zowoyoo / FonTicket / 票付通） | 逐个实现适配器 | 商务 |

七源全部**零编造端点**。没文档的源明确报「待商务确认」，
遇到未确认接口抛 `EndpointUnconfirmed` 并说清卡在哪、需要什么。

### 3.2 差业务决策（要人来定）

| 事项 | 为什么是决策不是工程问题 |
|---|---|
| 行级退款 | 需要「优惠券 / 税费 / 折扣怎么摊到每一行」的分摊口径 + 源侧支持部分取消。在这两样落地之前，系统对行级退款**明确报错**，不自己编一条分摊规则 |
| 按份数换源 | 售价行没有份数维度，要按份数换源得给价格加阶梯，是另一个增量 |
| 退款后的差价怎么处理 | 已成交的金额失去依据，差价退不退是业务决策 |

### 3.3 差顾客身份（要自己开工）

C 端购买链路的写侧（购物车 → 结算 → 下单 → 支付）还差**顾客账号体系与鉴权**。

运营台那套身份是**内部操作员**的身份，不是顾客身份，两者不是一回事。
C 端公开接口没有调用方身份，边界只能画在渠道上（只服务 `channel_type='b2c_own'` 且在营的渠道）。

### 3.4 已排期但未做

- 订单表分区、只读副本、源报文冷热分离（方案见 `docs/schema-design.md` §9）
- 接入层之上的业务编排作业（同步调度 / 改派 / 自动补报 / 退款重试）
- 源 SKU 下架后的自动改派作业（改派写路径已就位，缺触发它的编排）

## 5. 这个项目教会了什么

不是感想，是**在这个仓库里已经落成机制**的几条判断。写在这里是为了让下一个人
别把它们重新发明一遍。

### 5.1 「看不见」比「没有」更贵

供给形态对照视图（`v_variant_supply_forms`）存在的理由：配方与套装在路由视图里一行都没有。
不是它们不卖，**是读侧看不见它们在卖**。
看不见的后果不是少一行，是看不懂 —— 运营一个都答不上来。

同理，商品详情页之前只有「商品 × 渠道」的目录行，
运营答不出「绑了哪些源、判定依据是什么、有哪些可售单元」。

### 5.2 说不清楚的事不许猜

- 源侧没报库存 → 返回「不知道」（`known = false`），**不许返回 0**。返回 0 意味着「卖完了」，会让整个商品下架，比超卖更贵。
- 源侧把整套当一个 SKU 卖 → 从 `coverage` 看不出来是「一整套」还是「一张谁都能用的票」，所以**单独声明**，不推断。
- 组合没有单一源币种 → 汇率两列都空，那是「这里没有单一的值」，不是「同币种、汇率 1」。
- 人工写下的匹配依据 → 整段带出来，运营台不替机器猜它的结构。

### 5.3 机器不许洗掉人的判断

一次同步把人工判过的映射依据洗成机器的，那行**在库里还是合法的** ——
不变量不会变红，但人做过的工作没了。所以这条从约定变成了写路径门禁。

### 5.4 派生的数不许手抄

抄的那天是对的，加了一天条目的那天就有一处是旧的 ——
而「规格说 118、库里有 119」正是最费时间的一种不一致
（读者先信文档、再跑出另一个数，然后开始怀疑整个仓库）。

所以数只数一次（`make counts`），文档只引用不抄。

### 5.5 约定迟早被漏掉一次

「记得转义」「记得调 `store.Quote`」—— 这些在被赶工的时候是第一个被省掉的。
一次注入就是一次数据泄露。

所以值进 SQL 的转义从约定变成机制：绑定时转义 + AST 门禁。
门禁会放过裸数值位置（判据宁放过不误伤），所以它是第一道不是唯一一道 ——
真正的防线是写查询时走 `store.NewSQL`，它不留这个口子。

### 5.6 历史不可变，但事实不许消失

订单明细的展示内容走快照字段，不依赖当前商品表的 join 结果。
反过来，**事实不许被一次调用洗掉** —— 预订的请求报文改成合并而不是覆盖；
回调报文合并而不是覆盖（一次回调不许把发起时写下的承诺快照洗掉）。

### 5.7 残缺的东西不许悄悄变小

源 SKU 下架时，成分行**留着**，只是**没有价**。
丢掉的后果是配方静悄悄地变成了一个更小的套餐：少一个成分就按剩下的成分重新定价
（收 3 份入场的钱、出 1 张票，而 C 端构成读模型还写着 3 份入场）—— 卖错规格。

宁可少卖，不可卖错。
