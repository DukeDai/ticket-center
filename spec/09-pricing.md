### 4.5 按团报价与价格保护（2026-11-04 已决策并落地）

接入日游品类会撞上两个携程字段，这两条已定口径并有数据验证：

#### 按团报价（`package.priceSettingType = 4/5`）

按团报价时**「总价 = 单价 × 份数」不成立**，明细必须显式声明计价基准：

| `sales_order_item.pricing_basis` | 语义 | `unit_price` | `total_price` | `quantity` |
|---|---|---|---|---|
| `per_person`（默认） | 按人计价 | 每份单价 | `unit_price × quantity` | 份数 |
| `per_group` | 按团报价 | **人均分摊价** | **团总价**（直接落库） | 团内人数 |

- 团总价的真值记在明细快照 `detail_snapshot.group_total`（快照不可变，是历史真相）。
- 人均分摊价允许每人 1 分以内的取整误差：`abs(total_price - unit_price × quantity) ≤ quantity × 0.01`。
- `quantity` 始终是**人数**，不因按团计价而变成「团数」——实名采集、库存预占都依赖这个语义。
- **准入条件**：按团报价的商品接入前，本条口径必须先落地，否则不变量 5 会误报、金额会算错。

#### 价格保护（`resource.isPrivatePrice`）

源侧标记该变体**不得自主加价**，对客售价必须原样等于源方挂牌价。

关键点：**锁价是「采纳源」的属性，不是变体的固定属性**。
同一个变体若改由非保护源供货，售价即解锁。

| 层次 | 落地 | 含义 |
|---|---|---|
| 源侧 | `supplier_variant.is_price_locked` | 这个源变体受价格保护（携程 `isPrivatePrice`） |
| 平台侧 | `price_calendar.price_locked` | 这一行售价已锁定，**由采纳源派生**，不允许自主加价 |

不变量 37 / 38 双向把守：锁价行售价必须等于采纳源挂牌价；采纳了保护源的行**必须**锁价（防漏锁擅自加价）。

实测（北京环球影城）：同一商品下，老年票的最优源是 Trip.com（486 < Zowoyoo 505）→ 该行锁价，售价原样 498.00；
其余变体采纳 Zowoyoo（非保护源）→ 未锁，可自主定价。**同一商品里锁与不锁并存**，这正是「锁价随采纳源变化」的体现。

### 4.6 定价口径（2026-11-06 已决策并落地）

#### 定价只有一份实现

**`fn_price_variant(variant_id, date, context_channel_id, price_channel_id)` 是定价的唯一实现。**
视图、接入层（`tc-connect price`）、演练器（`scripts/mapping_dryrun.py`）、种子数据一律走它，
不允许任何一方另算一遍。

理由有两条，都是硬约束逼出来的：

- **钱必须是 `NUMERIC`**（AGENTS.md 硬约束 5）。Go 标准库没有十进制类型，Python 里 `float()` 算钱迟早差一分钱。
  唯一能同时被 SQL / Go / Python 三方够到、又保住精度的落点是数据库本身。
- **同一批源数据只能有一个价格。** 以前定价有三份实现（两个视图、一个 Python 块），
  外加种子数据里手写的数字；四者各自自洽，合起来给出的价不一样。这是真实事故的来源，不是洁癖。

`fn_reprice_rows()` 是重算入口：源成本变了、汇率快照换了、上架关系改了，统一重算，不写局部补丁。

#### 定价规则

规则写在 `channel_listing.price_policy`（jsonb），源侧的底线写在 `channel_listing_source.min_margin`：

```jsonc
{
  "mode": "cost_plus",        // cost_plus | per_group
  "percent": 16.0,            // cost_plus：成本加价百分比
  "min_margin": 0.12,         // 渠道要求的最低毛利率
  "floor": null,              // 售价下限（可空）
  "list_markup_percent": 12.5 // 划线价 = 售价 × (1 + list_markup_percent)
}
```

| 环节 | 口径 |
|---|---|
| 采纳源 | **就是路由选中的源**（`fn_route_candidates` 的 `route_rank = 1`）：在该上架关系绑定的启用源里，取**折算到基准币种后成本最低**的一个（并列时按 priority → fallback_order → 源商品 id 定序，保证可复现） |
| 成本 | `round(net_price × 留痕汇率, 2)`，汇率用**快照**（`as_of_date ≤ price_date` 的最新一条），缺快照则该候选源不参与比价 |
| 售价 | `max(成本 × (1 + percent/100), 成本 / (1 - 生效 min_margin), floor)`，三者取大，四舍五入到分 |
| 生效 min_margin | `max(渠道 price_policy.min_margin, 采纳源 channel_listing_source.min_margin)` —— **取严** |
| 划线价 | `round(售价 × (1 + list_markup_percent/100), 2)` |
| 折扣 | `round((划线价 - 售价) / 划线价 × 100, 2)` |
| 锁价行 | 售价 = `round(源挂牌价 × 汇率, 2)`，**不加价、不受 min_margin 约束、不造划线价**（划线价 = 售价，折扣 0） |
| 按团报价行 | 售价 = 源方团总价折算，平台不加价、不受 min_margin 约束（同上） |
| 结算币种 | 渠道专属行 = 该渠道的 `default_currency`；默认行 = 基准币种（`fn_price_row_currency(channel_id)`，不变量 44） |
| 汇率留痕 | `fx_rate` = 1 单位源币种 = ? 单位本行币种（8 位小数）；`fx_as_of` = 这次折算实际依赖的快照日期；**同币种不折算 → 因子 1、快照日期 NULL** |

锁价与按团报价豁免 min_margin 的理由：这两种情况下**售价由源方或商务约定，平台无权加价**。
平台若为满足毛利率而抬价，就是擅自加价 —— 携程价格保护直接违约。

#### 选源与定价同源

**`fn_route_candidates(variant_id, date, channel_id, target_currency)` 是选源的唯一实现**，
路由视图 `v_variant_routing_candidates` 与定价函数 `fn_price_variant` 都从它取候选与排序。

以前两边各排一次序：视图按「折算到基准币种的成本」排，定价函数按「折算到目标币种的成本 + 源商品 id」排。
两把尺子不完全一样，一旦数据一变就会分叉 —— 分叉的后果是**按 A 源的价格卖、按 B 源出票**：
客诉说不清、对账对不上、佣金算不出。现在排序键只有一份，分叉在结构上不可能发生，
不变量 43 负责证明它没被改回两份。

排序键的顺序也是决策，写在这里以免各自理解：

1. **折算到基准币种的成本** —— 比价是自动选源的目的（§3.2）；
2. `priority`（越小越优先）、`fallback_order` —— 只在成本相同时决定先后；
3. `supplier_product_id` —— 兜底，保证同样的输入永远得到同样的选择。

候选必须同时满足：渠道上架关系里挂着且启用、源变体覆盖得住这个变体、当天有可用报价、
**币种能折算到基准币种与目标币种**（缺快照的源不参与比价 —— 不可比的成本不能被当成便宜的候选）。

#### 汇率留痕的口径

折算经基准币种中转（`1 base = rate(quote)`），所以一次折算最多依赖两份快照：源腿与目标腿。

- `fx_rate`：**1 单位源币种 = fx_rate 单位本行币种**，8 位小数（`price_calendar.fx_rate` 是 `NUMERIC(18,8)`，函数返回值与落库值逐位相同）。
- `fx_as_of`：两腿都有快照时取**较晚**的那一天。取较晚是安全的 —— 两腿各自选中的都是「价格当日或之前最近的一份」，
  所以用这个日期重算，任一腿选中的还是原来那一份，因子逐位相同。留痕日期因此可以独立复算，不必再问原始价格日期。
- **同币种不折算 → `fx_rate = 1`、`fx_as_of = NULL`。** 没折算过就不留假快照 —— 留一个日期等于声称「这次折算用过这份汇率」，
  对账时要去查一份并不存在的折算。

不变量 45 就是拿留痕日期回去复算因子，对不上就说明留痕自相矛盾。

#### 售价行是派生物，不是真相

`price_calendar` 里写的是「卖哪一行」（变体 × 日期 × 渠道），**金额字段全部由定价函数填**。
不变量 41 拿函数重算一遍并逐字段比对：任何从别的路径写进去的金额都会被抓出来。

#### 定价侧不变量（39-45）

| # | 不变量 |
|---|---|
| 39 | 在售源价格的币种必须可折算到基准币种（缺汇率快照的候选源不参与比价） |
| 40 | 售价行的成本必须等于采纳源成本按留痕汇率折算的结果 |
| 41 | 在售售价行必须等于定价函数的输出（成本 / 售价 / 划线价 / 折扣 / 锁价 / 成本来源）；定价算不出结果的行必须没有价格 |
| 42 | 非锁价售价行的毛利率必须达到生效 min_margin（锁价与按团报价豁免） |
| 43 | 定价采用的源必须是路由选中的源（否则会「按 A 源的价格卖、按 B 源出票」） |
| 44 | 售价行的币种必须等于该行的结算币种（渠道专属行用渠道结算币种，默认行用基准币种） |
| 45 | 售价行留痕的汇率与快照必须自洽（留痕日期能独立复算出同一个折算因子；同币种不留快照） |

### 4.7 交易侧不变量（46-53，2026-11-06 补充）

交易侧的门禁与供给/展示侧分开住在 `v_invariant_checks_tx` 里，
（`v_invariant_checks` 是各主题视图的并集，分组见 §4 开头。）
拆开住是为了不把 45 条不变量抄一遍 —— 抄一遍就会分叉，分叉的门禁等于没有门禁。

| # | 不变量 |
|---|---|
| 46 | 订单状态必须可从初始状态沿合法边到达（没有「凭空出现」的状态） |
| 47 | 订单明细状态必须可从初始状态沿合法边到达 |
| 48 | 预订状态必须可从初始状态沿合法边到达 |
| 49 | 凭证状态必须可从初始状态沿合法边到达 |
| 50 | 已确认订单必须有 confirmed/ticketed 的预订（订单不能凭空确认） |
| 51 | 已出票凭证必须挂在 confirmed/ticketed 的预订上 |
| 52 | 订单状态与履约状态必须一致（fulfilled ⟺ fulfillment_status='fulfilled'；取消/失败/退款的订单不得是 fulfilled） |
| 53 | 订单小计必须等于明细合计（比小计不是总额：优惠券在订单层减，总额 = 小计 - 折扣 + 税由不变量 4 把守） |

「合法边」的定义在 `state_transition` 表里（`db/migrations/003_transaction_state_machine.sql`），
由函数 `fn_guard_state_transition`（挂在 `trg_*_status_guard` 触发器上）强制：
不在表里的流转写不进去，改不动。
