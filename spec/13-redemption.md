### 4.11 核销侧不变量（65-68，2026-11-07 补充）

核销侧的门禁单独住在 `v_invariant_checks_redemption` 里，
拆开住的理由同上：不把已有条目抄一遍。

| # | 不变量 |
|---|---|
| 65 | 已核销的凭证必须有一条成功的核销记录 |
| 66 | 一张凭证最多只能成功核销一次 |
| 67 | 成功核销必须用尽该凭证的入场额度且额度账对得上 |
| 68 | 成功核销必须发生在凭证的有效期内 |

这四条守的是「这张票到底用没、用了几次、用掉多少、是不是在有效期内」。

- 券标着 `used` 却找不到成功的核销记录（不变量 65）—— 状态和事实分叉了，
  要么是有人手改了券状态，要么是核销记录被删了。票务上这叫「无凭入场」。
- 一张券成功核销了两次（不变量 66）—— 重复入场是票务欺诈的入口。
  这条不是靠约定防的，是靠 `voucher_redemption` 上的唯一索引
  `ux_redemption_single_success`（`WHERE result='success'`）挡住。
- 成功核销没有把入场额度用尽、或者额度账对不上（不变量 67）——
  按人计价的一人一券消耗 1，按团报价的整团一券消耗整团人数，账要能对上。
- 券还没到有效期或已经过期却核销成功（不变量 68）—— 券没到日子就进不了场。

### 5.8 核销写路径（2026-11-07 落地）

前面三段写路径（下单 / 履约 / 退款）都通了，票也发出去了，但**票发出去就没人能用了**：
`voucher_redemption` 有表、状态机里有 `issued → used` 这条边，写路径是空的。
连带的后果是退款里「有已核销的票不许整单退」那条分支也永远走不到 ——
没有东西能把票变成 `used`。

现在这一段有唯一实现：`fn_redeem_voucher()`（`db/migrations/008_redemption.sql`）。

**这一段有九条口径，写在前面。**

第一，**一次核销 = 一次扫票，核销记录永远追加**。成功失败都落一条，不覆盖、不去重。
重复扫票本身就是事实（票务欺诈的入口），压掉就看不见了。

第二，**状态效果幂等**：一张券最多成功核销一次，由 `voucher_redemption` 上的唯一索引
`ux_redemption_single_success`（`WHERE result='success'`）兜底，不靠约定。
第二次扫同一张券 → `result='duplicate'`，并带回第一次核销的记录 id 与时间
（`original_redemption_id` / `original_scanned_at`），调用方据此对账。
**网络重试丢了响应和恶意重复扫码在这里是同一件事，不该分成两条路。**

第三，**额度一次用尽**。一人一券的券一次扫一张（消耗 1），按团报价的整团一券一次扫全团
（消耗整团人数）。成功后券从 `issued` 变 `used`，触发器落一条 `VoucherRedeemed` 领域事件。
前提是凭证是一次性入场凭证 —— 多次入场的通票还没进模型，真要支持这一条要重新设计。

第四，**过期 / 作废 / 已退款 / 未出票的券不认核销，但都要落一条记录并写清原因**：
`not_yet_valid` / `past_valid_to` / `voucher_void` / `voucher_refunded` /
`voucher_not_issued` / `no_entitlement` / `entitlement_exhausted` / `order_refunding` /
`gate_inactive` / `already_redeemed`。「为什么这张票进不去」是闸机和客服都要看到的事实。
（券状态本身已经是 `expired` 的记 `voucher_expired`；状态不在已知集合里的记
`voucher_status_<状态>`，不留空。）

第五，**正在退款的订单不认核销**（钱在退的时候把人放进去，退款就退不干净）。
这里刻意**不锁订单行**：退款路径的加锁顺序是「订单 → 凭证」，反向加锁会死锁；
读一次快照判断即可 —— 退款在核销之后发起的话，退款路径会撞上「有已核销的票」并要求人工处理。

第六，**票码撞车不能猜**。不同源可能发了一样的票码：有闸机就按闸机所属的源收窄候选集，
收窄不出来就报错。票码不存在 / 不唯一是调用方的问题，不是扫票的结果 —— 报错而不是留记录。

第七，**过期只落核销记录，不改券状态**。券状态留给过期作业统一改（**这个作业还没做，见 §7**），
一件事一件事分开，才说得清是谁在什么时候把哪张票判成什么。

第八，**`voucher.used_channel` 记的是这张券所属订单的销售渠道**（`channel.code`），
用于按渠道对账；闸机 / 操作员 / 设备另记在 `voucher_redemption` 上。

第九，**幂等靠状态，不靠幂等键**。核销记录必须每次都追加，不能靠幂等键去重。

函数清单：

| 函数 | 干什么 | 幂等口径 |
|---|---|---|
| `fn_redeem_voucher` | 扫一次票：判能不能进场、用尽额度、改券状态、落核销记录 | 幂等靠状态：唯一索引挡住第二次成功核销，第二次记 `duplicate` |

返回值是一张「这次扫票的结果」，不是异常：`success` / `duplicate` / `expired` /
`revoked` / `failed`。前四档是这张券的处境，`failed` 是这次没过的原因（写在 `reason` 里）。
**只有票码不存在 / 不唯一才报错** —— 券过期、券作废、券还没出票、订单在退款，
这些都是扫票的正常结果，要返回给闸机看，同时在库里留一条记录。

Go 侧新增 `internal/redemption`：拼参数、收结果、把库的报错原样带出去。
**不在 Go 里判断能不能进场，不在 Go 里算该扣多少额度，不在 Go 里改券状态** ——
理由与 `internal/order` / `internal/fulfillment` / `internal/refund` 相同。
CLI 是 `tc-connect redeem scan|show`。
