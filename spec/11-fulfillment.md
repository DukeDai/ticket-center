# 履约侧不变量与履约写路径（支付 → 预订 → 出券）

### 4.9 履约侧不变量（55-60，2026-11-07 补充）

履约侧的门禁单独住在 `v_invariant_checks_fulfill` 里，
拆开住的理由同上：不把已有条目抄一遍。

| # | 不变量 |
|---|---|
| 55 | 每一笔成功的支付金额必须等于订单应付金额 |
| 56 | 订单标着已支付，就必须有一笔成功的支付记录（状态与事实一致） |
| 57 | 已确认 / 已履约订单的**每一条明细**都要有 confirmed/ticketed 的预订（不变量 50 只看订单级，这里逐行看） |
| 58 | 预订的源必须等于订单明细的采纳源（不能「按 A 源的价格卖、按 B 源出票」） |
| 59 | 预订的源场次必须来自场次级绑定（规范场次 ↔ 源场次 ↔ 源商品），不是按日期猜的 |
| 60 | 订单的履约状态必须与明细的出票情况一致（状态是结论，结论只有一个算法） |

这六条守的是「事实与状态不许分叉」。分叉的典型样子有三个：

- 钱记上了，订单状态还挂在 `awaiting_payment`（不变量 56）；
- 明细票已出齐，订单还停在 `booking_pending`（不变量 60）；
- 预订挂在源 A，明细的采纳源是源 B（不变量 58 —— 这是客诉说不清、对账对不上的那个）。

不变量 58 还有一条配套口径：**改派备源不是「换源出票」**，
而是重下一行明细并重新定价。切换已支付订单的采纳源会让已成交的金额失去依据。

### 5.6 履约写路径（2026-11-07 落地）

到 §5.5 为止，下单写路径通了，但支付之后没人写：钱怎么入账、预订谁建、
票码怎么变成券、订单什么时候算履约完成 —— 全是空的。
现在这一段有唯一实现：`db/migrations/005_fulfillment.sql` 里的那组函数。

**这一段有五条口径，写在前面，因为它们决定了所有函数长什么样。**

第一，**订单的履约状态不归调用方写**。调用方只报事实
（付了、订了、出票了），状态由 `fn_apply_order_fulfillment()` 从明细的实际出票情况推出来。
「明细全发齐 → fulfilled；有发出但没发齐且没有在途 → partially_fulfilled；
每条明细的预订都确认了 → confirmed；全挂了 → failed」。
只有一套算法，就不会有第二处算错。

第二，**预订的源场次必须来自 `product_session_source` 的绑定**。
同一个商品同一天可能有好几个场次（上午场 / 下午场 / 夜间场），
按日期去 `supplier_session` 里找一条「同商品同日期」的记录是猜，猜错就是发错场的票。
绑定找不到就报错，不猜（不变量 59）。

第三，**票码与持票人一一对应**。要发几张券由计价口径决定
（按人计价一人一券，按团报价整团一券），票码数必须等于还要发的张数 ——
少一个就报错，不拿一张券顶两个人的票。

第四，**预订的单位是源 SKU，不是一个成分**（2026-11-08 修订，理由见 §5.13 第五条）。
源卖的是 SKU，我们就按 SKU 订：一张订单明细里，同一个源 SKU 在同一个源场次上
只订一次。参数化源尤其要紧 —— 成人票与儿童票是**同一个**源 SKU
（人群是购买时选的一档），按成分建预订就是同一个源 SKU 订了两次。
这条预订覆盖哪些成分由 `fn_booking_components()` 推出来
（按「明细 + 源 SKU + 源场次」），不另存一份，免得两份事实分叉。

第五，**票码不许是券号派生的**（2026-11-08 补充，不变量 94）。
源侧给了票码就用源侧的；源侧没给就自己生成一个 128 位随机码（`VC-` + 32 位十六进制）。
以前拿券号（`VC` + 日期 + 连号）当票码 —— 券号是连号的，**猜得到**；
票码是闸机认的东西，猜得到就等于没有闸机。
券号留作内部标识：对外展示、对账、核销查的都是券号。

第六，**预订的请求报文是合并，不是覆盖**（2026-11-09 补充，018 迁移）。
`fn_create_bookings()` 往 `booking.request_payload` 写的是**我们打算发出去的请求**
（订单号 / 份数 / 成分 / 快照），`fn_request_booking(p_request)` 写的是
**接入层实际发出去的那一份**。原来是覆盖，且 `p_request` 的默认值是 `'{}'` 而不是 NULL，
所以「不传报文」也会把整列洗掉。
套装的份数与入场份数就靠这两个字段区分（1 套 vs 3 份）——
洗掉之后「预订的单位是套还是份」这件事在库里就没处可查，对账只能靠猜。
现在改成合并：我们写的事实留着，接入层这次发的报文盖在上面。

函数清单：

| 函数 | 干什么 | 幂等口径 |
|---|---|---|
| `fn_record_payment` | 支付入账：金额必须等于订单应付，币种必须一致 | 按渠道流水；同一笔重放返回原记录，另一笔打进来 = 重复收款，报错要退款 |
| `fn_create_bookings` | 给已支付的订单建预订（一个源 SKU 一条预订） | 幂等键按「明细 + 源 SKU」定；已建过的不重复建 |
| `fn_request_booking` | 发起预订（`pending → requested`） | 重试也走这里，`attempt_count` 递增 |
| `fn_record_booking_attempt` | 归档一次尝试：报文、HTTP 状态、耗时、错误分类 | 同一次尝试可重复归档（upsert），撞唯一索引报错等于把重试堵死 |
| `fn_complete_booking` | 落源侧结果（`requested → confirmed/failed/cancelled`） | 确认必须带源侧预订号 |
| `fn_issue_voucher` | 出券 | 已发的券不重发；票码数必须对得上 |
| `fn_retry_booking` | 失败重报（`failed → pending`） | 设 `next_retry_at` |
| `fn_apply_order_fulfillment` | 推导订单履约状态 | 同样的事实推出同样的状态 |

几个容易被忽略但必须写死的细节：

- **支付的 `status` 与 `payment_status` 在同一条 `UPDATE` 里改。**
  只改 `payment_status` 会留下一张「钱记上了、状态还挂在 `awaiting_payment`」的单：
  下一棒按状态推进就卡住，而且卡在一个看不出原因的地方。
- **确认预订必须带源侧预订号。** 没有它就无法回头找源对账 ——
  出问题时连「找哪一笔」都做不到。这条在写路径上挡，不等不变量事后报警。
- **「源先确认、票后到」是常态。** `fn_complete_booking` 的 `p_issue_voucher=false`
  先把订单推进到 `confirmed`，票到了再调 `fn_issue_voucher`。
  强行要求「确认即出券」会在票晚到时卡死整条链路。
- **失败不等于完了。** 源侧失败（库存被占位、超时）只是这条预订的事，
  订单可以走 `partially_fulfilled`，重报把预订放回 `pending` 再试。

**预订仍然不是订单聚合的一部分。** §3.3 规定 booking 是独立聚合：
源侧故障不能阻塞订单聚合，所以预订只在支付成功之后创建。
订单的状态推进只读预订的事实，不等预订。

Go 侧新增 `internal/fulfillment`：拼参数、收结果、把库的报错原样带出去。
不在 Go 里判断状态该往哪走，不在 Go 里算履约状态，不在 Go 里拼票码与持票人的对应关系 ——
理由与 `internal/order` 相同。金额一律以字符串进出（Go 标准库没有十进制类型）。
CLI 是 `tc-connect fulfill pay|book|request|attempt|complete|issue|retry|show`。
