## 4.3 C 端展示与购买（2026-10-28 补充）

第一版设计只覆盖了供给侧（怎么把源接进来），C 端「展示」与「购买」的领域模型是空缺的。
本次补齐，详见 `docs/c-end-model.md`。

### 展示侧

| 能力 | 落地 |
|---|---|
| 列表页卡片 | `c_product_card`（读模型，按 channel × product × locale 物化，带 `synced_at` 标注新鲜度） |
| 日历格子 | `c_product_calendar`（售罄/闭馆日**也要有格子**，前端才能画灰、禁用点击） |
| 详情页内容 | `product_highlight` / `product_inclusion` / `product_note` / `product_location` / `product_review` / `tag` |
| 多语言 | 内容表一律带 `locale` 列；`product.attributes` 只保留**语言无关的结构化事实** |

### 购买侧

| 能力 | 落地 |
|---|---|
| 购物车 | `cart` / `cart_item`（含加购时的 `price_snapshot`） |
| 库存预占 | `inventory_hold`（TTL + 状态机 + 过期自动释放） |
| 优惠券 | `coupon` / `coupon_redemption`，订单侧记 `coupon_id` + `discount_breakdown` |
| 实名表单 | `checkout_requirement`（按商品/票种/渠道定义字段与校验）+ `order_holder`（采集的输入） |
| 核销端 | `gate` / `gate_operator`，`voucher_redemption` 关联 |

### 读模型纪律

1. **读模型可随时重建**，主数据永远是唯一真相。
2. `v_c_readmodel_drift` 检测卡片起价与价格日历是否已不一致，`drifted=true` 即刷新作业漏跑。
3. 列表页的价格与库存必须来自**同一次刷新**，不允许卡片上拼两个新鲜度不同的数据源。

## 4.4 变体与可售单元（2026-11-04 补充）

### 为什么必须加这一层

环球影城这类商品的维度不是「商品 × 人群」两层，而是：

```
人群(成人/儿童/老年) × 票种(一日/双日) × 园区范围(单园区/园区通票) × 加购件(快速通行证)
```

旧模型把「人群」硬编码进 `ticket_type`、把「日期」硬编码进 `product_session`，
维度一多就无处安放。更麻烦的是**两个源对同一商品的分解方式根本不同**：

| 源 | 分解方式 | 后果 |
|---|---|---|
| Trip.com | 固定组合 SKU（一个 SKU = 一个完整组合） | 一个源变体对一个规范变体 |
| Zowoyoo（自由行） | 参数化售卖方案（人群/园区是下单参数），且是聚合层 | 一个源变体覆盖多个规范变体 |

`product_mapping` 回答不了「这个源到底能供哪些组合」，
商品级路由 `v_source_routing_candidates` 也回答不了「这一单该走哪个源」。
**实测：商品级路由视图对北京环球影城输出 0 行**（见 `db/verify.sql` H4）。

### 模型要点

| 概念 | 落地 | 说明 |
|---|---|---|
| 可售单元 | `product_variant` | **product 的下一级不是 `ticket_type`，而是变体** |
| 维度 | `product_axis` / `product_axis_option` | 人群沿用 `ticket_type`（历史订单语义不变），其余维度全部配置化 |
| 变体取值 | `product_variant_option` | 一个轴一个取值；多选语义由取值自身的集合承载（`option_attrs.park_ids`） |
| 可叠加件 | `product_variant_relation` | 基础票 ← 快速通行证 / 园区升级（`variant_role='addon'`） |
| 源侧变体 | `supplier_variant` | 固定组合型源的 SKU、参数化源的售卖方案 |
| 覆盖映射 | `supplier_variant_mapping.coverage` | **不是一对一，而是「覆盖」**：声明该源变体能满足哪些轴取值 |

**核心规则：`coverage` 决定「这个源能不能履约这个组合」。**
变体要求的每一项能力（人群 + 各轴取值）都必须落在 `coverage.axes[axis]` 内、
且不在 `coverage.excludes` 内，否则该源不得参与该变体的自动路由。

### 旧结构是本模型的特例

「两层 SKU」= 只有人群一个轴的变体模型。迁移规则：

1. 每个 `(product, ticket_type)` 生成一个 `base` 变体；
2. 每个 `supplier_ticket_type` 生成一个源变体，与规范票种做 1:1 精确覆盖映射；
3. 售价/成本价回填变体 id。

**不推翻任何已有表结构**，所有新增列都是 `ALTER TABLE ... ADD COLUMN`。

### 变体侧不变量（27-34）

| # | 不变量 |
|---|---|
| 27 | 变体的轴取值必须属于该商品的轴定义 |
| 28 | 同一商品内变体指纹 `variant_key` 不得重复 |
| 29 | 在售变体必须有人群或轴取值定义，不允许空变体占位 |
| 30 | 覆盖映射必须真的覆盖目标变体的全部能力（覆盖不全不得挂 `active`） |
| 31 | 在售售价日历必须绑定变体（售价粒度不得停留在商品/票种层） |
| 32 | 订单明细的变体商品必须与明细商品一致 |
| 33 | 加购件变体必须挂在至少一个基础变体上（不得成为孤儿） |
| 34 | 有售价的变体在其上架渠道必须至少有一个可履约源 |
| 35 | 同一订单内同一商品的多个变体必须使用同一日期 |
| 36 | 订单小计必须等于明细金额之和（按人计价与按团计价都适用） |
| 37 | 锁价售价必须等于采纳源的挂牌价（价格保护，携程 `isPrivatePrice`） |
| 38 | 采纳价格保护源的售价行必须锁价（防止漏锁导致擅自加价） |

### 5.18 C 端只读 API 的口径（2026-11-10 落地）

读模型建好了，差异事实也进读模型了，但**没有请求链路** ——
差异还是只有查库的人看得见。§5.18 把 C 端的读侧开成 HTTP 接口：
`internal/capi` + `cmd/tc-api`。

**这一段有七条口径，写在前面。**

第一，**请求链路只读读模型，不 join 主数据，也不重算事实**。
端点打在 `c_product_card` / `v_c_listing_feed` / `v_c_variant_feed` /
`v_c_variant_composition` / `c_variant_calendar` 上 ——
有效天数、成分份数、可履约源数都是库里算好的，API 只把它们带出去。
在 Go 侧重算一遍就是第二份实现（硬约束 10 / 24）。

第二，**渠道是必答的那一半**。C 端读模型是按渠道建的：
一个套餐上了两个渠道就有两份成分明细，不按渠道过滤，
「2 份成人 + 1 儿童」会被数成两遍（§5.14 第四条）。
所以带渠道维度的端点**必须传 `channel_id`**，缺了就报错，
不给「全部渠道」这个默认值。

第三，**渠道还必须是对外服务的自营 C 端**。C 端接口是匿名的 ——
没有调用方身份，边界只能画在渠道上。`channel` 表里还有 B 端分销、
企业客户、供应商直销、内部运营，它们的读模型与自营 C 端在**同一个库里**，
价格、币种、税费、结算各是一套：换个渠道号就能读到别家的目录与报价，
那是**跨渠道的数据泄露**，不是「参数没校验」的小问题。
所以只服务 `channel_type = 'b2c_own'` 且 `status = 'active'` 的渠道，
其余一律回 403；渠道不存在与渠道不对外服务给**同一个答复** ——
不给调用方一个能枚举渠道的探针。
所有收 `channel_id` 的端点走同一个闸门（`requireChannel`），不许各自再解析一遍。

第四，**金额与 NUMERIC 一律以字符串出**。Go 标准库没有十进制类型，
浮点会把 2470.80 变成 2470.7999999999997（硬约束 5）。

第五，**有效期终点由库算好，前端不许自己加一天**。
日历格子的 `valid_to` 是库算的（格子日期 + 有效天数），
应用侧加一天和库里加一天，早晚有一天对不上（不变量 77）。

第六，**参数不合法就报错，不猜、不糊过去**。`channel_id` 必须是正整数、
`locale` 只能由字母数字下划线短横组成、日期必须 `YYYY-MM-DD` ——
校验不过就回 400 并说清楚差在哪，不静默取默认值。

第七，**写侧暂不开成 HTTP 接口**。下单 / 支付 / 出券各有唯一实现
（`fn_place_order` / `fn_record_payment` / `fn_issue_voucher`），
但系统里**还没有调用方身份**：没有顾客账号体系，
把下单开成匿名接口等于把订单入口暴露给任何人。
读侧不需要身份，先落地；写侧等鉴权那一层有了再开。

端点：

| 端点 | 读什么 | 对应 C 端链路 |
|---|---|---|
| `GET /healthz` | 数据库通不通 | 探活 |
| `GET /api/v1/products?channel_id=&locale=&limit=&offset=` | `c_product_card` + `v_c_listing_feed` | ① 浏览 |
| `GET /api/v1/products/{product_id}/variants?channel_id=` | `v_c_variant_feed` | ③ 选变体（差异事实） |
| `GET /api/v1/variants/{variant_id}/composition?channel_id=` | `v_c_variant_composition` | ③ 套餐由谁组成 |
| `GET /api/v1/variants/{variant_id}/calendar?channel_id=&from=&to=` | `c_variant_calendar` | ④ 看日历 |

表里带 `channel_id` 的端点**只服务在营的自营 C 端渠道**（第三条）：
其余渠道回 403，理由与答复跟渠道不存在时一模一样。

两条列表口径：

- **下架的卡片不出列表**（`status = 'offline'`），**售罄的仍在**（`status = 'sold_out'`）——
  前端画灰就行，不该让用户以为这个商品不存在。
- **变体行的 `audience` 对组合是空的**，人群在 `combo_audience`（各成分的人群编码）与
  成分清单里 —— 组合没有单一人群，「2 成人 + 1 儿童」是前端按 locale 拼的（硬约束 9）。

**退款口径的展示只带两个字段。** 变体行给 `refundable`（布尔）与
`refund_fee_percent`（字符串，来自读模型），这两个是用户下单前要知道的。
**`refund_cutoff_hours` 不出 C 端**：截止时长是**相对某个参照点**的
（场次开始前 48 小时），C 端读侧没有确定的参照点，把一个裸小时数带出去，
前端只能自己拿「现在」去减 —— 减出来的不是承诺，是猜。
真要展示「什么时候截止」，得由库按具体场次算好再给，
那是另一条读模型的事，不在 §5.18 这四个端点里。

这两个字段是**读模型里的值**，不是写路径的判定：
写路径那一侧按 `fn_refund_policy` 判（[`spec/12-refund.md`](12-refund.md) §5.7）。
读侧展示的承诺与写侧执行的承诺必须是同一份，
所以字段的来源是读模型而不是 Go 侧重算（硬约束 10 / 24）。

包与二进制：

| 位置 | 干什么 |
|---|---|
| `internal/capi` | C 端只读 API：路由、参数校验、读模型查询 |
| `cmd/tc-api` | API 服务：起停、优雅收尾、起服前先探库 |
