### 4.14 读模型侧不变量（76-77，2026-11-07 补充）

异构差异在主数据里已经表达清楚了（轴 / 覆盖 / 有效期），但 **C 端看不到它们**。
读模型只带价格与可售天数，前端要显示「这是几日的票、覆盖哪些园区、能不能退」，
只能在请求链路里 join 主数据 —— 而请求链路不许 join 主数据。
最要命的是有效期：两日票和单日票在日历上长得一模一样，
用户按「当天有效」理解两日票，第二天拿着票到门口才发现进不去。
门禁住在 `v_invariant_checks_readmodel` 里。

| # | 不变量 |
|---|---|
| 76 | C 端读模型里的变体事实必须与主数据一致 |
| 77 | 变体日历格子的有效期终点必须等于格子日期加有效天数 |

- 读模型与主数据分叉（不变量 76）—— 刷新作业漏跑时这里当场红。
  读模型可重建，但重建前它就是错的：页面会显示「一日票」而发出来的是两日券。
- 日历格子的有效期终点算错（不变量 77）—— 前端不许自己加一天。
  前端加一天和应用侧加一天，早晚有一天对不上；终点由库算好，前端只读。

### 5.11 C 端读模型刷新口径（2026-11-07 落地）

到 010 为止，差异在主数据里已经说清楚了，但 **差异没走到 C 端**。
读模型（`c_product_card` / `c_variant_calendar`）只带价格与可售天数。
C 端要显示「几日的票 / 覆盖哪些园区 / 能不能退」，只有两条路：
在请求链路里 join 主数据，或者把差异事实也放进读模型。
前者违反读模型纪律（请求链路不许 join 主数据），所以走后者。

**这一段有五条口径，写在前面。**

第一，**差异事实进读模型，不进请求链路**。新增 `c_variant_facts`：
一行一个 (渠道, 可售单元)，带人群 / 轴取值 / 有效天数 / 退款口径。

第二，**事实只写一份**。读模型里的每个字段都从 `v_variant_comparison` 取，
不重算 `valid_days`、不重算 `axes` —— 重算就是第二份实现，
而两份实现的后果是「展示说两日票、发出来的是一天有效期的券」。

第三，**读模型不许与主数据分叉**（不变量 76）。刷新作业漏跑当场报出来。

第四，**日历格子带有效期终点**。`c_variant_calendar.valid_to = 格子日期 + 有效天数`，
前端不用自己加一天（不变量 77）。

第五，**哪些变体上这个渠道由日历格子决定**。刷新建事实，也清掉已经没有格子的旧事实
（读模型可重建，主数据是唯一真相）—— 不然 C 端会看到「有事实、没格子」的幽灵变体。

表与视图：

| 表 / 视图 | 干什么 |
|---|---|
| `c_variant_facts` | 变体级差异事实读模型（渠道 × 可售单元） |
| `v_c_variant_feed` | C 端变体读视图：差异事实 + 本渠道价格区间与可售天数，一行一变体 |
| `v_invariant_checks_readmodel` | 读模型侧不变量（76-77） |

刷新作业的口径仍然只在库里的 `fn_refresh_read_models()` 里：
`002` 建的那一版被 `011` 整体替换（返回值多一个计数，行类型变了，
PostgreSQL 不许改函数的返回类型，所以是 DROP + CREATE）。
Go 侧是 `internal/readmodel`（只调库里的函数、只读结果，不另算口径）。
差异的读侧是 `internal/variant`（只读三张视图，不重算有效天数与覆盖判定）。
