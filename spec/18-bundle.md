### 4.19 套装侧不变量（95-101，2026-11-09 补充）

套装是异构融合的**第三种形态**。§4.15 / §4.16 讲的是配方型组合：
我们自己把几个源 SKU 按份数拼成一个可售单元。
套装是另一种：**源侧把整套当一个 SKU 卖** —— 一个 `ZWO-FAMILY-SET` 就是一整套，
订一次、发三张票。

从 `coverage` 看不出一个源 SKU 是「一整套」还是「一张谁都能用的票」——
两者都能覆盖住同一个可售单元，但成本、预订单位、库存池、有效期全都不一样。
**看不出来就不能猜**，所以套装必须单独声明（`supplier_variant_bundle`），
不许从覆盖关系推断。

门禁住在 `v_invariant_checks_bundle` 与 `v_invariant_checks_bundle_020` 里。

| # | 不变量 |
|---|---|
| 95 | 一个可售单元的供给形态不许既是配方又是套装（形态唯一） |
| 96 | 套装的成分必须与规范声明逐项对得上（不少、不多、份数一致） |
| 97 | 套装的有效期必须盖住成分的有效期窗口 |
| 98 | 套装成本分摊必须精确等于套装成本 |
| 99 | 套装订单的入场份数必须等于套装声明的份数乘套餐份数 |
| 100 | 按源票种查库存不许跨源票种相加（源侧没报就说不知道） |
| 101 | 套装在同一个池子上的需求不许超过落单时看到的可售数 |

- 形态不唯一（不变量 95）—— 同一个可售单元既声明了配方又声明了套装，
  定价走哪条分支说不清：成本会算两遍，或者只算一遍。
  收三个人的钱、出一张票是最贵的一种错。
- 成分对不上（不变量 96）—— 源侧说「2 成人 + 1 儿童」，规范侧说「2 成人」：
  多发一张票，或者多收一份钱。份数不一致就是卖错规格。
- 有效期盖不住（不变量 97）—— 源侧整套只管 1 天，规范侧的成分管 2 天：
  客户第二天到门口进不去。钱收了、票买了、门不认 —— 本项目最贵的一种 bug。
- 分摊不守恒（不变量 98）—— 分摊到成分是为了对账：
  Σ 分摊 × 套数必须精确等于整套成本 × 套数。差一分钱，这笔账在对账时查不出来。
- 份数不守恒（不变量 99）—— 套装有两个单位：**售卖单位是套**，**入场份数是份**。
  混了就少发票（发了 2 张票，收了 3 个人的钱）。
- 池子串了（不变量 100）—— 套装的库存池是**源侧那个整套票种**，
  不是同一场次里随便哪个票种的余量。源侧没报这个票种的库存就是**不知道**，
  拿别的票种的余量顶上 = 用儿童票的库存卖整套票。
- 逐明细看不出超卖（不变量 101）—— 两条明细各自记着「还剩 1 套」，
  各要 1 套，各自都过；加在一个池子上就是 2 套，超卖。
  需求必须**按池子加总**再比。

套装的构成同样是**结构化事实**（人群编码 / 份数 / 各自管几天），不是拼出来的文案 ——
展示文案由前端按 locale 拼（硬约束 9）。

### 4.20 供给形态对照侧不变量（102-104，2026-11-09 补充）

异构融合有三种形态，但**读侧只认得一种**。`v_variant_routing_candidates`
与 `v_variant_source_coverage` 走的是 `fn_route_candidates`，
而 `fn_route_candidates` 只建模方向 A（一个源 SKU 覆盖多个可售单元）。
配方与套装的可售单元在那些视图里**一行都没有** ——
不是它们不卖，是读侧看不见它们在卖。

看不见的后果不是「少一行」，而是**看不懂**：同一个商品下，
两个几乎一样的家庭套餐（配方 ¥1656.48、套装 ¥1740.00），
交付的却是同样的 2×成人 1 日 + 1×儿童 1 日。哪个在卖、卖得掉不掉、
差在哪 —— 运营侧一个都答不上来。

门禁住在 `v_invariant_checks_supply_forms_021` 里。

| # | 不变量 |
|---|---|
| 102 | 声明过的供给形态不许在对照视图里消失 |
| 103 | 供给形态对照视图的成本必须等于定价函数算的成本 |
| 104 | 供给形态对照视图的入场份数必须等于 C 端构成读模型的份数 |

- 形态消失（不变量 102）—— 声明了配方或套装，对照视图里却一行都没有。
  那一路供给在运营侧是**隐形的**：没人知道它存在，没人知道它卖不卖得掉。
  更糟的是它还在真实地卖 —— 订单里有它，只是报表里没有它。
- 成本分叉（不变量 103）—— 对照视图说成本 A，定价函数说成本 B，
  就是两份实现。对照视图的成本必须**取定价函数那个**，
  不是「各源里的最小值」：选源按基准币种排序（`fn_route_candidates`），
  最小值按本行币种排，渠道币种不是基准币种时这两个「最小」不是同一个源。
- 份数分叉（不变量 104）—— 入场份数来自 `fn_variant_composition`
  （与 C 端构成读模型同一个来源）。对照视图自己重数一遍 = 第二份实现，
  分叉就是卖错规格。

对照视图的口径在 §5.16。

### 4.21 供给形态不许缩小侧不变量（105-107，2026-11-10 补充）

异构融合的每一种形态都是**几份东西拼起来的**。配方是「2 份成人 + 1 份儿童」，
套装是「源侧那个整套」。这些东西只要有一个**从源侧下架**，
拼出来的就不再是原来那个东西了。

原来的口径是：解析成分时 `JOIN supplier_variant ... AND status = 'active'`，
下架的源整个消失。于是：

- **配方静悄悄地变成了另一个套餐**。少一个成分，定价函数看到的就是
  「少一个成分的套餐」，按剩下的成分重新定价 —— 收 3 份入场的钱，出 1 份票。
  C 端构成读模型还写着 2 个成分 / 3 份入场，读侧与写侧当场分叉。
- **套装的形态行整个从对照视图里消失**。不是「卖不掉」，是「看不见」——
  「这个变体没人供」和「没人看得见它有人供」长得一模一样。

源侧下架是**事实**，我们改不了源侧，也不该为了留住事实去改写历史订单。
但我们不能把「少一个成分的套餐」当成「这个套餐」卖出去 ——
**宁可少卖，不可卖错**。

门禁住在 `v_invariant_checks_supply_form_shrink_022` 里。

| # | 不变量 |
|---|---|
| 105 | 配方的成分不许因为源 SKU 下架而消失 |
| 106 | 成分的源 SKU 下架时配方套餐不许还能卖 |
| 107 | 套装的源 SKU 下架时套装不许还能卖 |

- 成分被静悄悄丢掉（不变量 105）—— 声明过的成分与解析出来的成分必须一样多。
  少一个，配方就不是原来那个配方了。
- 缩小后还能卖（不变量 106 / 107）—— 源 SKU 下架时，
  **对照视图不许说能供，定价函数不许给出价格**。两边都要守：
  只守一边的话，运营看到一个「能供」的形态就敢上架，
  或者收银台按一个已经配不齐的套餐收钱。

口径在 §5.17。

### 4.22 可履约源数侧不变量（108，2026-11-10 补充）

C 端的日历格子带一个 `source_count`，注释写的是「有几个源能履约这个变体」。
那一列是给前端的关键信号：**只有 1 个源的组合没有备源**，源挂了要提前知道
（`docs/c-end-model.md` §3.3）。

原来的口径只在**单张**形态上算得对：刷新作业数的是「源映射 × 当天的源侧报价」的行数，
而配方与套装按设计**没有源映射**（不变量 81：组合不许直接挂源映射）——
所以它们的格子一律是 0。

0 的意思是「一个源都供不了」。而这些组合在对照视图里明明
`can_fulfil = true`、`supplier_count = 1`、售价也摆在那里。
C 端读到的却是「0 个源」：**一个在卖的套餐被说成没有供给**，
前端就该按没有供给处理 —— 要么下架，要么报缺货。

门禁住在 `v_invariant_checks_supply_source_count_023` 里。

| # | 不变量 |
|---|---|
| 108 | 日历的可履约源数必须等于供给口径算出来的源数 |

- 源数被写成 0（不变量 108）—— 日历的可履约源数必须等于
  `fn_variant_supply_source_count()` 算出来的数。谁把它改回
  「源映射 × 报价行数」（配方与套装没有源映射 → 0），当场红。
- 刷新作业漏跑（不变量 108）—— 日历里躺着的是旧数，当场红
  （与第 76 条同一个道理：读模型可重建，但重建前它就是错的）。

口径在 §5.19。

### 5.15 套装的售卖口径（2026-11-09 落地）

套装是**源侧把整套当一个 SKU 卖**。源侧没有我们的配方，
所以套装的成本、预订单位、库存池全都不是配方那一套 ——
但它也不是单张票（一条预订 → 三张入场券）。

**这一段有十条口径，写在前面。**

第一，**套装必须单独声明**。`supplier_variant_bundle` 记「规范变体 ← 整套源 SKU +
源侧整套的有效期」，`supplier_variant_bundle_part` 记「这套包含什么、几份」。
不许从 `coverage` 推断：一个源 SKU 覆盖住整个可售单元，
可能是「一整套」，也可能是「一张谁都能用的票」。

第二，**三个单位不许混**：

| 单位 | 是什么 | 存在哪 |
|---|---|---|
| 售卖单位 | 套 | 订单明细的 `quantity` |
| 成分单位 | 预订的单位（一个源 SKU 一条预订） | `booking` 的份数 |
| 入场份数 | 发的券的张数 | 成分行的 `admission_quantity` |

一套「2 成人 + 1 儿童」= **1 套 / 3 份入场**。
拿套数去比份数，或者拿份数去比套数，都会判成「少发了票」。

第三，**成本来自源侧那个整套报价，不重新选源**。套装的成本就是那个整套 SKU 的
报价（1500），不是成分单价相加，**也不重新路由**。
重新选源 = 配方变摆设 = 按 A 源的价格卖、按 B 源出票。

第四，**成本分摊到成分只是为了对账**。分摊按**每套**口径精确到两位小数，
最后一份吸收余数，Σ 分摊 × 套数 = 整套成本 × 套数（不变量 98）。
分摊值落在 `price_calendar.rule->'combo'` 与成分行上 —— 同一个事实只写一处。

第五，**库存池按源侧那个票种算**。套装不是「每个成分各扣各的」，
是扣**源侧整套票种**的池子（`fn_available_qty` / `fn_reserve_qty` 加了带
`source_ticket_type_id` 的重载）。预占**一条**，份数是**套数**。
池子的取数口径见第九、第十条。

第六，**预订的单位是套，不是份**。一条预订对应一个源 SKU；
`request_payload.quantity` 是套数，`request_payload.admission_quantity` 是入场份数。
`fn_request_booking` 因此**合并**而不是覆盖请求报文（018 迁移）：
我们写的事实（套数 / 入场份数 / 成分 / 快照）留着，
接入层这次发出去的报文盖在上面。事实不许因为一次调用就没了 ——
对账时要靠它分清「买了一套」和「发了三张票」。

第七，**出券逐成分发**。一条预订覆盖几个成分就发几张，各发各的张数、
各按各的持票人与有效期。票码数仍然必须等于还要发的张数。

第八，**有效期是源侧声明的**。`supplier_variant_bundle.valid_days` 是源侧整套能用的天数，
必须盖住规范侧成分窗口的并集（不变量 97）。套装在 C 端的有效期终点仍由
`fn_variant_validity_days` 算，不许在同步作业里另算一遍。

第九，**池子的余量不许跨源票种相加**。查某个源票种的可用数时，
可用数只能来自**这个源票种自己的快照**；源侧没报这个票种的库存就是
**不知道**（`known = false`、可用数为空），不许拿同一场次里别的票种的余量顶上
（不变量 100）。用儿童票的库存去卖整套票，卖出去的钱收不回。

第十，**需求按池子加总，不许逐明细各算各的**。两条明细各自记着「还剩 1 套」，
各要 1 套，各自都过；加在一个池子上就是 2 套，超卖。
落单时预占必须按**池子**汇总需求量再比（不变量 101），
对账用视图 `v_bundle_pool_demand`（订单 × 池子：需求套数 / 落单时还剩多少 /
当时知不知道）。

表与视图：

| 表 / 视图 | 干什么 |
|---|---|
| `supplier_variant_bundle` | 套装的声明：规范变体 ← 整套源 SKU + 整套有效期 |
| `supplier_variant_bundle_part` | 套装包含什么：成分 + 份数 |
| `fn_bundle_components()` | 套装成分的唯一读法：成本、份数、票种、有效期 |
| `v_bundle_gap` | 套装卖不掉的原因（按天列：没有报价 / 没有场次 / 有效期盖不住 / 可售数未知） |
| `v_variant_bundle` | 套装的供给形态（读侧：成分构成 + 有效期窗口 + 缺口诊断） |
| `v_variant_bundle_part` | 套装成分明细（读侧） |
| `v_invariant_checks_bundle` | 套装侧不变量（95-99） |
| `v_bundle_pool_demand` | 套装池子上的需求对账（订单 × 池子：需求套数 / 落单时还剩多少） |
| `v_invariant_checks_bundle_020` | 套装库存侧不变量（100-101） |

接入层读侧是 `internal/variant.BundleRows` / `BundlePartRows`
（只读视图，不重算份数与有效期），命令行是 `tc-connect variant bundle`。

### 5.16 三种供给形态的对照口径（2026-11-09 落地）

异构融合有三种形态，各自有各自的读法（`v_variant_comparison` 认得差异，
`v_variant_source_coverage` 认得方向 A 的覆盖，`v_variant_bundle` 认得套装），
但**没有一个视图能把三种放在一起看**。运营侧要回答的问题是跨形态的：
这个商品今天有几种供给方式？各卖多少钱？哪一种卖不掉、为什么？

§5.15 的套装走完了成交，但读侧还差一环 ——
`v_variant_routing_candidates` 与 `v_variant_source_coverage` 走
`fn_route_candidates`，而它只建模方向 A。配方与套装的可售单元在那些视图里一行都没有。

**这一段有六条口径，写在前面。**

第一，**对照视图是一行一个「可售单元 × 一天 × 一个渠道 × 一种形态」**。
粒度定在「天 × 渠道」是因为成本、场次、汇率全都随这两样变；
定在「天 × 渠道 × 形态」是因为形态不同成本口径就不同（单张是选中源的成本、
配方是 Σ 成分单价 × 份数、套装是源侧那个整套报价）。

第二，**形态的取舍标准与定价函数逐条对齐**。
配方不可售的五种情况（成分缺价 / 成分不在同一场次 / 成分跨源 / 成分锁价 / 按团报价）、
套装不可售的七种情况（当天没有源侧报价 / 没声明成分 / 没绑源场次 / 锁价 /
有效期盖不住成分窗口 / 没有源侧票种 / 按团报价），
与 `fn_price_variant` 的两个分支逐条相同。
**不一样的话，同一个可售单元在两处会说两件事。**

第三，**成本取定价函数那个**。单张形态的成本取 `route_rank = 1` 的那个候选，
不是各源里的最小值 —— 选源按基准币种排序，最小值按本行币种排，
渠道币种不是基准币种时这两个「最小」不是同一个源（不变量 103）。

第四，**能供的时候不许报缺口**。形态整体的缺口只在这个形态**真的卖不掉**时才报；
逐源的缺口（覆盖不住 / 当天没价）在候选明细里。
两样混在一起就是「✓ 能供，却说当天没报价」—— 自相矛盾的话比没有话更坏。

第五，**缺口要说人话**。缺口短语与既有口径同源：
「成分当天没有报价」「成分不在同一场次」「成分跨源」「成分锁价」「按团报价」
（配方），「套装当天没有源侧报价」「套装没有声明成分」「套装没有绑定源场次」
「套装锁价」「源侧整套有效期盖不住成分窗口」「套装没有源侧票种（算不出库存池）」（套装）。
看不出来就说看不出来，不猜。

第六，**入场份数只写一份**。对照视图的 `admission_quantity` 来自
`fn_variant_composition`（与 C 端构成读模型同一个来源），
不许自己重数（不变量 104）。

表与视图：

| 表 / 视图 | 干什么 |
|---|---|
| `v_variant_declared_forms` | 声明过的形态（单张 / 配方 / 套装）逐天在场次上有没有声明 |
| `v_variant_supply_forms` | 三种形态放在同一张表上对照：源、成本、缺口、入场份数 |
| `v_invariant_checks_supply_forms_021` | 供给形态对照侧不变量（102-104） |

接入层读侧是 `internal/variant.SupplyFormRows`（只读视图，不算成本、不算份数），
命令行是 `tc-connect variant supply`。

### 5.17 源 SKU 下架时的供给形态口径（2026-11-10 落地）

异构融合的形态是**拼**出来的：配方是几个源 SKU 按份数拼，
套装是源侧把整套当一个 SKU 拼。拼的零件下架了，拼出来的东西就不是原来那个东西。

**这一段有五条口径，写在前面。**

第一，**声明过的成分不许因为源 SKU 下架而消失**。
成分行留着，只是**没有价**。源的可用性从「决定这一行在不在」
改成「决定这一行有没有价」—— 这是 `fn_combo_components` 与
`fn_bundle_components` 唯一的语义改动，函数签名一个字没动。

第二，**少了价的成分 = 这个形态整体卖不掉**。
定价函数的 `n_priced = n_parts` 门禁已经守着这一条
（少一个成分 → 有一个成分没价 → 定价函数不返回价格），
不用另写一套判定。

第三，**形态不许从对照视图里消失**。单张、配方、套装都一样：
源 SKU 下架时形态行仍然在，`can_fulfil = false`，缺口点名
「源 SKU 已下架」「成分的源 SKU 已下架」「套装的源 SKU 已下架」。
看不见的形态等于不存在的一路供给。

第四，**残缺的套餐不许报成本**。成分缺一个时 `cost_in_target` 留空 ——
残缺套餐的钱不是这个套餐的钱，留着会让运营拿一个残缺套餐的数去对账。

第五，**缺口要说人话，理由不许互相盖住**。
源 SKU 下架时只报「源 SKU 已下架」这一条，不叠「当天没有报价」——
源还在、只是下架了，报价其实还在。事实要说准。

表与视图：

| 表 / 视图 | 干什么 |
|---|---|
| `fn_combo_components` | 配方的成分行：源 SKU 下架时这一行仍然在，只是没有价 |
| `fn_bundle_components` | 套装的成分行：整套的源 SKU 下架时成分行仍然在，只是没有整套价 |
| `v_variant_supply_forms` | 三种形态的对照：形态不许消失，缺口说清为什么 |
| `v_invariant_checks_supply_form_shrink_022` | 供给形态不许缩小侧不变量（105-107） |

### 5.19 可履约源数的口径（2026-11-10 落地）

「有几个源能供这个可售单元（这一天、这个渠道）」由**一个函数**算：
`fn_variant_supply_source_count(variant, date, channel)`（`db/migrations/023_supply_source_count.sql`）。

三种形态各按自己的供给路径算，但只有这一个出处：

| 形态 | 供给路径 | 源数怎么数 |
|---|---|---|
| 单张 | 一个源 SKU 覆盖住这个可售单元（方向 A） | 路由能选出的源（`fn_route_candidates`：绑定 + 覆盖 + 当天有价 + 汇率可得） |
| 配方 | 几个源 SKU 按份数拼（方向 B） | 成分的源 SKU（成分当天有价才算能供） |
| 套装 | 源侧把整套当一个 SKU 卖 | 源侧那个整套 SKU 的源 |

四条口径写死：

- **源数不是成分数。**「2 份成人 + 1 份儿童」是 3 个成分、**1 个源**。
  那一个源同时供着那三个成分 —— 备源只有一个，不是三个。
- **源数不是价格行数。**同一个源当天有两行报价（两个票型），还是 1 个源。
  按行数数，「有备源」这句话就是假的。
- **单张按路由算。**选源与定价同源（硬约束 15）：能选出来的源就是能供的源。
  少算一个源 = C 端说「有备源」，而那个源在这个渠道上根本没绑。
- **日历的 `source_count` 与对照视图的 `supplier_count` 是两件事。**
  日历答「这一天有几个源能供」；对照视图答「这个形态由哪几个源组成」
  （声明层面 —— 源下架了也还数着它，那是 §5.17 刻意保留的事实）。
  混成一个数才是把两件事搅在一起。

落点：日历刷新作业（`fn_refresh_read_models`）与组合 / 套装日历同步
（`fn_sync_combo_calendar`）都改走这个函数，C 端 API 的日历端点直接把它带出去。

表与函数：

| 位置 | 干什么 |
|---|---|
| `fn_variant_supply_source_count` | 唯一实现：几个源能供这个可售单元（这一天、这个渠道） |
| `v_invariant_checks_supply_source_count_023` | 可履约源数侧不变量（108） |
