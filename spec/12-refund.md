# 退款侧不变量与退款写路径（发起 → 放行 → 完成）

### 4.10 退款侧不变量（61-64，2026-11-07 补充；124-126 于 2026-11-14 补充）

退款侧的门禁单独住在 `v_invariant_checks_refund` 里，
拆开住的理由同上：不把已有条目抄一遍。
承诺侧的门禁住在 `v_invariant_checks_refund_policy` 里。

| # | 不变量 |
|---|---|
| 61 | 退款金额合计不得超过订单实付金额（退超了就是公司赔钱） |
| 62 | 已退款订单必须有一条成功的退款记录，且金额等于该单承诺的应付退款额 |
| 63 | 已退款订单的每一条明细必须已取消或已退款（不能留着还在「已确认」的票） |
| 64 | 已退款订单不能留着成功的支付记录（钱退了、支付记录还写着成功，对账时两笔对不上） |
| 124 | 退成功的单，其退款金额必须等于按该单承诺算出的应付退款额 |
| 125 | 承诺为「不可退」的商品，不许有退成功的单 |
| 126 | 每一张退款单（含未落结果的）的金额必须等于按承诺算出的应付退款额 |

这四条守的是「退了钱，事实要跟着变」。退钱这件事最容易出的岔子是
**只改了订单状态，没改它底下的事实**：

- 订单标成 `refunded`，明细还挂在 `confirmed`（不变量 63）；
- 订单标成 `refunded`，支付记录还是 `succeeded`（不变量 64）；
- 退了两笔，合计超过订单实付（不变量 61）；
- 订单标成 `refunded`，退款单上的钱不是承诺的那个数（不变量 62）。

这四条与履约侧的 55-60 是同一个道理的两面：
履约侧守「事实与状态不许分叉」，退款侧守「退钱之后事实必须一起改」。

62 的「金额」这一半对照的是**承诺算出的应付额**而不是订单实付（§5.7 第二条）：
没有手续费承诺时两者相等，有手续费承诺时差的那笔是**承诺过的手续费**，
不是错的。

124-126 守的是另一件事：**我们对客户承诺的退款口径必须真的被执行**。
承诺（`product.refund_policy`）已经展示给客户了（C 端 `refundable` /
`refund_fee_percent`），但退款路径此前不读它 —— 承诺写在那里，
没人执行，承诺与事实就分叉了。这三条让承诺进入退款写路径（§5.7 第六条）。

### 5.7 退款写路径（2026-11-07 落地）

履约通了之后，钱收了、票出了，但**钱怎么退回来**没人写：
`sales_refund` 有表、状态机里有边，写路径是空的。
现在这一段有唯一实现：`db/migrations/007_refund.sql` 里的三个函数。

**这一段有五条口径，写在前面。**

第一，**退款作用域是整单**。按行退（部分明细退）需要一张
「优惠券 / 税费 / 折扣怎么摊到每一行」的分摊口径，还需要源侧支持部分取消 ——
那是业务决策，不是工程决策。在这两样落地之前，系统对行级退款明确报错，
而不是自己编一条分摊规则。

第二，**退款金额必须等于按承诺算出的应付退款额**。少退客户会投诉，多退公司自己承担。
这一条由 `fn_request_refund()` 把守：申请金额与应付退款额不等就报错。
应付退款额不是一个常量，它由该单的**退款承诺**算出（第六条）——
没有手续费承诺时就是订单实付（`sales_order.total`），
有手续费承诺时是 `实付 × (1 − fee_percent)`，四舍五入到两位。

**`sales_refund.amount` 是实退给客户的钱**（净额）。
这一点写死，是因为这一列是对账时读的那一列：
它必须等于**真的从我们账上出去了多少钱**，
否则「客户收到 1490.83、退款单写着 1656.48」就再也对不上了。
手续费是**另一次收款**（我们向客户收的取消手续费），
不是退款的一部分，它记在承诺快照里（第六条）。
没有手续费承诺时两者相等（净额 = 实付），所以这一条不改变今天的行为。

第三，**「有没有真的收到钱」看支付记录，不看订单状态**。
订单状态是人写进去的（可能写错），支付记录是事实。
所以判退资格时查的是 `sales_payment` 里 `status='succeeded'` 的金额合计 ——
没有成功的支付记录就报错「无款可退」。订单状态只是第一道粗筛。

第四，**幂等键必填**。重放一次退款就是多退一次钱。
抢键用 `INSERT ... ON CONFLICT DO NOTHING`（不走「先查后插」），
同一个键配不同内容直接报错 —— 静默返回上一笔等于吞掉一次退款。

第五，**退款必须先放行才能落结果**（2026-11-08 补充，不变量 93）。
退款是三步：发起（`requested`）→ 放行（`approved`）→ 落结果（`succeeded` / `failed`）。
以前 `fn_complete_refund` 只拦终态，一笔还在 `requested` 的退款能被直接结掉 ——
**放行这一步形同虚设**，审批形同不存在，钱却真的退了。
现在 `fn_complete_refund` 只接受 `approved` 的退款单，其他状态当场报错；
放行时记下放行人（`sales_refund.approved_by`）与放行时间（`approved_at`），
走到终态的退款单这两个字段都必须在（不变量 93）。

第六，**退款承诺必须被执行者执行**（2026-11-14 补充，不变量 124-126）。
`product.refund_policy` 是**我们承诺给客户的口径**，
已经展示在 C 端（`refundable` / `refund_fee_percent`）——
但此前没有任何一条业务路径读它来判定能不能退。
承诺写在数据里、没人执行，承诺与事实就分叉了：
C 端写着「可退 10% 手续费」，退款路径却按全额退，
少收的钱公司自己承担，客户看到的口径与实际拿到的钱对不上。

**这一条有三个字段，各自有不同的语义与执行方式。**

| 字段 | 语义 | 执行方式 |
|---|---|---|
| `refundable` | 这个商品退不退 | **硬门禁**：承诺为不可退时，退款路径当场报错 |
| `cutoff_hours` | 开场前多少小时之后不能退 | **硬门禁**：距开场不足 N 小时的单拒退 |
| `fee_percent` | 取消手续费比例（可缺省） | **金额口径**：应付退款额 = 实付 × (1 − fee_percent) |

`refundable` 与 `cutoff_hours` 是**资格**，`fee_percent` 是**金额**。
两者的失败后果不一样：资格不满足 → 报错，这笔退不了；
金额不符 → 报错，这一笔退的数不是承诺的那个数。

**承诺只有一处读法**：`fn_refund_policy(p_order_id)`。
它解析这一单**实际生效**的承诺，返回资格判定与应付退款额。
生效口径是：渠道的覆盖（`channel_listing.refund_policy_override`）
盖住商品的承诺（`product.refund_policy`），**逐字段覆盖**——
覆盖里没写的字段沿用商品的承诺，不是整份替换。
（渠道承诺是给渠道单独谈的条件；一个渠道只改手续费比例、
不改「能不能退」，这不是要改能不能退。）

执行点在**两处**，不是一处：
- **发起时**（`fn_request_refund`）判资格、校验金额；
- **放行时**（`fn_approve_refund`）**重判一遍**。

为什么放行时要重判：发起与放行之间有时间差，
`cutoff_hours` 会被这段时间吃掉 —— 发起时距开场 50 小时（承诺 48 小时），
放行时距开场 30 小时，这一笔就已经越过截止点了。
只判一次的话，截止点就是在发起那一刻判定的，不是承诺里写着的时点。
所以发起判一遍（早退，早报错），放行再判一遍（临近放行时的真相）。

**截止点的参照点**是这一单明细的**最早场次开始时间**：
`product_session.start_at`，没有 `start_at` 时退回 `product_session.session_date`。
取最早的那个场次：订单里有多条明细时，截止点由**最先开始的那一场**决定 ——
后一场还没开始不代表前一场还没开始。
（订单里所有明细的场次都取不到时没有参照点，此时不按截止点拦 ——
读不到就是不知道，不拿别的场次顶上，与硬约束 34 同一条口径。）

**手续费承诺没有源侧的对应物**。所有源都不声明退款条款
（`docs/connector-contract.md` 里只有 `refund(externalBookingId, req)` 这个调用形状），
所以 `refund_policy` 纯粹是我们自己的承诺，语义由我们定。
这一条写清楚，是因为它决定了「能不能让源侧决定退多少」：**不能**。
源侧不报退款条款，我们就不许拿源侧的退票结果去反推应付退款额。

**手续费收了，钱记在哪。** 手续费是**我们**向客户收的，不是源侧的结算手续费
（`settlement_line.fee_amount` 是源侧结算口径，两者不是一件事）。
所以手续费要留在退款单上：退款单的 `amount` 是**实退给客户的钱**（净额），
**手续费金额**记在 `sales_refund.raw_payload->'policy'` 里（承诺快照，
与退款额一起冻结），与明细快照（`detail_snapshot`）同一条口径：
**冻结当时的事实**。
这样对账时看的是当时的承诺，不是今天的承诺。

**承诺快照里存四个数**，不存一个：

| 键 | 是什么 |
|---|---|
| `refundable` | 发起时生效的「退不退」 |
| `cutoff_hours` | 发起时生效的截止点（小时） |
| `fee_percent` | 发起时生效的手续费比例 |
| `expected_amount` | 由上面三个算出的应付退款额 |

`expected_amount` 是**发起时算出来的那个数**，不是「发起时有多少钱」。
两者相等，但不混为一谈：发起时订单实付 1656.48、手续费 10% →
应付退款额 1490.83。快照里两个都记（实付在承诺快照外，
它是订单的事实；应付额在快照里，它是承诺算出来的）。

**不变量 62 的「金额」这一半因此改成对照承诺算出的应付额**，不再是对照 `order.total`。
没有手续费承诺时两者相等（应付额 = 实付），所以这条门禁今天的行为不变；
有手续费承诺时，对照的是承诺而不是实付 ——
承诺说退 1490.83 就退 1490.83，与实付 1656.48 的差是**手续费**，
那笔差是承诺过的，不是错的。

**不变量 124-126 复查已发生的事实**：
退成功的单，其退款金额必须等于按承诺算出的应付额（124）；
承诺不可退的商品不许有退成功的单（125）；
每一张退款单（不管落没落结果）的金额都必须等于应付额（126）。
124 与 126 的分工：126 管**每一张**退款单（发起时就对上了），
124 只管**退成功**的那些（走完流程的钱必须对得上）。
两条看的是同一份快照，但落点不同：126 抓发起时金额就已经错的单子，
124 抓那笔金额在发起时是对的、落结果时被改掉的单子。
这三条读的是**退款单与承诺快照的对照**，不读订单状态 ——
订单状态是人写的，承诺快照与金额是事实。

**62 与 124 的分工**：62 从**订单**这一头看（一个标成已退款的订单，
它的退款单加起来对不对）；124 从**退款单**这一头看（退成功的那笔，
金额对不对）。同一份快照，两个落点：
62 抓的是「订单与退款单对不上」，124 抓的是「退款单与承诺对不上」。
没有手续费承诺时 124 是 62 的推论（应付额 = 实付），
有手续费承诺时 62 若还对着 `order.total` 比就会误报 ——
所以 62 的对照口径与 124 一致，都是承诺算出的应付额。

函数清单：

| 函数 | 干什么 | 幂等口径 |
|---|---|---|
| `fn_refund_policy` | 解析这一单生效的退款承诺：资格判定 + 应付退款额（唯一读法） | 纯读函数 |
| `fn_request_refund` | 发起退款：按承诺判资格、校验金额、落退款单、订单推进到 `refunding` | 幂等键必填；同键异内容报错 |
| `fn_approve_refund` | 人工放行（`requested → approved`）：**按承诺重判一遍资格** | 重复放行幂等 |
| `fn_complete_refund` | 落退款结果：成功时一次改完事实与订单，失败时把订单退回去 | 成功重复落幂等；失败是终态，重试要发起新的一笔 |

`fn_refund_policy` 是**纯读函数**，只拼参数、只读结果 ——
它不写任何东西，是「承诺在哪里」与「承诺意味着什么」的唯一实现。
发起与放行都调它，所以「承诺怎么算」只有一份，
不存在「发起按一套算、放行按另一套算」的分叉。

几个容易被忽略但必须写死的细节：

- **订单在「发起」时就推进到 `refunding`，不是在「成功」时。**
  发起的那一刻就该拦住履约推进 —— 免得一边退一边出票。
  触发器因此落一条 `RefundRequested` 领域事件。
- **退款失败时订单要能退回去。** 发起时把订单原状态记进
  `sales_refund.previous_order_status`，失败时照它恢复。
  为此在 `state_transition` 里补了 `refunding → paid/confirmed/
  partially_fulfilled/fulfilled/booking_pending` 这几条「往回走」的边 ——
  原来的状态机只往前走，没有退路。
  退不回去的状态就留在 `refunding` 等人处理，不硬改。
- **失败的退款单是终态。** 要重试得发起一笔新的退款请求（新的幂等键）：
  订单已经退回原来的状态，再走一遍 `refunding → refunded` 会缺边。
- **有已核销的票不许整单退。** 票已经用掉了，钱不该全退 ——
  这笔要人工处理，系统明确报错，不自己判断该不该退。
- **退款成功时事实一起改**：明细 → `cancelled`/`refunded`，
  凭证 → `refunded`，预订 → `cancelled`，支付 → `refunded`，
  订单 → `refunded` + `payment_status='refunded'` + `fulfillment_status='cancelled'`。
  由不变量 61-64 把住。
- **退款单要带上承诺快照**（`raw_payload->'policy'`）：发起时生效的
  `refundable` / `cutoff_hours` / `fee_percent` 与算出的应付额一起冻进去。
  承诺以后改了（商品改手续费比例），历史退款单上留的是**当时**的承诺 ——
  与明细快照、定价快照同一条口径：历史不可变（硬约束 7）。
  不变量 124-126 复查时读的就是这份快照，不是商品表当前的承诺。
- **回调报文合并而不是覆盖。** `fn_complete_refund` 落回调报文时是
  `raw_payload = raw_payload || v_callback`，不是整列盖掉。承诺快照是发起时
  写下的事实，一次不带回调报文的退款完成调用不该把它洗成空对象 ——
  洗掉了，62 / 124 / 126 复查的对照右边就成了 0，已退款的订单全部报违规。
  合并前先摘掉回调报文里的 `policy` 键：那是渠道串了字段，不是我们要让的
  事实被改写。同一口径在预订请求报文上已经修过一次
  （`018_booking_request_payload_merge.sql`），这里是第二次落地
  （`033_refund_payload_merge.sql`）。

Go 侧新增 `internal/refund`：拼参数、收结果、把库的报错原样带出去。
不在 Go 里判断能不能退，不在 Go 里算该退多少，不在 Go 里改订单状态 ——
理由与 `internal/order` / `internal/fulfillment` 相同。
金额一律以字符串进出。CLI 是 `tc-connect refund request|approve|complete|show`。
