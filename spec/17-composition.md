### 4.15 组合映射侧不变量（78-81，2026-11-07 补充）

异构融合有**两个方向**：

- **方向 A**（已有）：一个源 SKU 覆盖多个规范变体 —— zowoyoo 的 `ZWO-1D-BASE`
  一个源变体同时能装出成人 / 儿童 / 老年三个可售单元。
  门禁住在 `v_invariant_checks_core` 里（第 30、43 条等）。
- **方向 B**（本节）：一个规范变体由多个源 SKU 按数量组成 —— GlobalTix 的
  「家庭套餐（2 大 1 小）」，源侧是**一条**组合表达式
  （`80041201-8004120101|2 + 80041201-8004120102|2 + ...`），源侧一次预订就下完。

方向 B 在 011 为止没有模型，于是那份报文只能被判成「当前模型表达不了的源侧结构」——
报告里写着，系统没法卖。门禁住在 `v_invariant_checks_composition` 里。

| # | 不变量 |
|---|---|
| 78 | 组合映射的成分必须来自同一个源（一次预订只给一个源） |
| 79 | 组合映射的每个成分必须覆盖得住声明的规范组件（且数量一致） |
| 80 | 规范侧的组件声明必须与源侧成分逐项对得上（每个组件有且只有一个对应成分） |
| 81 | 组合变体不得直接挂源映射（它的供给只走配方） |

- 成分跨源（不变量 78）—— 跨源的组合是另一个形状的问题（要拆单），不是这里解决的。
- 成分顶错了组件（不变量 79）—— 「源侧给的是成人门票，我们声明的组件是儿童票」
  是最贵的一种错：客户按家庭套餐付款，拿到的是两张成人票。
- 两侧对不上（不变量 80）—— 少一个成分 = 源侧少给一份；多一个 = 我们多卖一份；
  数量不一致 = 卖错规格（2 大 1 小发成 1 大 1 小）。
- 组合直接挂源映射（不变量 81）—— 那会让定价函数用**一个**源 SKU 的成本
  给整张套餐定价：收三个人的钱，出一张票。

### 4.16 组合售卖侧不变量（82-88，2026-11-07 补充）

§4.15 的四条管的是**映射**对不对得上。组合真的卖出去之后，
还有七件事必须成立 —— 门禁住在 `v_invariant_checks_combo` 里。

| # | 不变量 |
|---|---|
| 82 | 订单明细的成分必须属于该明细商品的变体（成分不能跑到别的商品里去） |
| 83 | 明细成本必须等于 Σ 成分单价 × 成分数量（定价与履约不许各算一遍） |
| 84 | 明细的入场份数必须等于配方的份数之和 × 套餐份数（要发几张券由配方说了算） |
| 85 | 成分必须来自同一个源，且与明细的采纳源一致（一次预订只给一个源） |
| 86 | 已出券的明细，权益额度必须覆盖成分的入场份数（券不够 = 门打不开） |
| 87 | 同一张订单明细里同一个源 SKU 只能有一条预订（不许把同一个源 SKU 订两次） |
| 88 | 订单进入预订阶段后，预订与成分必须双向对齐（每个成分都要被订到，每条预订都要有成分） |

- 成分跑到别的商品（不变量 82）—— 组合的成分是「这个商品的某一档」，
  不是任意变体。跑错了就是给错产品发券。
- 成本与定价对不上（不变量 83）—— 定价按 Σ 成分成本 × 数量算，
  履约按成分行的成本留痕；两边对不上就是「按 A 的成本卖、按 B 的成本记账」。
- 份数对不上（不变量 84）—— 2 份成人 + 1 份儿童要发 3 张券，
  按明细份数（1 份套餐）发就是发一张。
- 跨源或与明细不一致（不变量 85）—— 一次预订只给一个源。
- 权益额度不够（不变量 86）—— 一人一券消耗 1，按团报价整团一券消耗整团人数；
  额度不够就是钱收了门不认。
- 同一个源 SKU 订了两次（不变量 87）—— 参数化源里成人票与儿童票是**同一个源 SKU**
  （`ZWO-1D-BASE`，人群是购买时选的一档）。按成分建预订就是同一个源 SKU 被订两次：
  源侧看到两张订单单，我们这边一条客户订单对两个源单号，对账对不上；
  源侧只确认了其中一个成分时，整张套餐是半成品 —— 收了三个人的钱出了两张票。
- 预订与成分对不齐（不变量 88）—— 漏订 = 套餐少一份；悬空预订 = 订了没人要的东西。

### 4.17 组合在 C 端的差异（89-92，2026-11-08 补充）

组合是**我们自己的配方** —— 源侧没有对应的商品条目，目录同步作业看不见它。
所以 §4.14 的读模型纪律对它不自动成立：源侧同步跑得再勤，
组合在 C 端也是一片空白。门禁住在 `v_invariant_checks_readmodel` 里。

| # | 不变量 |
|---|---|
| 89 | 组合的有效期必须恰好等于成分窗口的并集（不是最短，也不是和） |
| 90 | C 端的组合构成必须与主数据一致（多一行、少一行、份数或天数变了都算分叉） |
| 91 | 组合的日历格子必须带价格（挂着一个卖不了的套餐 = 白占一个位置） |
| 92 | 组合的成分折算留痕必须自洽（同币种不折算、跨币种必须留快照日期且因子能复算） |

- 组合的窗口算错（不变量 89）—— 「2 份两日成人 + 1 份一日儿童」这张套餐，
  客户拿到的是**两天**的票：取最短就是第二天进不去，取和（3 天）就是多赔客户一天。
  89 的两边独立读：组合那边走 `fn_variant_validity_days`，
  成分那边直接从轴选项读 —— 拿自己证明自己永远绿灯。
- 构成与主数据分叉（不变量 90）—— 读模型里的份数被改坏（2 份写成 5 份），
  C 端就显示「5 份成人」，实际只发 2 份。
- 组合的格子没有价格（不变量 91）—— 卖不了的套餐不该出现在日历上。
- 组合的折算留痕坏了（不变量 92）—— 组合的成本来自配方而不是某一个源商品，
  所以 `cost_source_product_id` 是空的：不变量 45（普通可售单元的折算留痕）
  按这个字段 join 源价行，**直接跳过组合**。
  没人复查 = 留个假快照日期都没人知道，对账时这笔折算查无此账。
  92 逐成分查：同币种 → 因子 1、快照日期为空；跨币种 → 必须有快照日期，
  且因子能用这个日期独立复算出来。

组合在 C 端的构成是**结构化事实**（人群编码 / 份数 / 各自管几天），
不是拼出来的文案 —— 展示文案由前端按 locale 拼（硬约束 9）。

### 4.18 收紧口径（93-94，2026-11-08 补充）

这两条不是新业务，是把已有的两步动作**变成必经之路**：
原来它们可以在实现里被绕过，绕过之后系统照样跑，只是没人知道钱是谁放行的、
闸机认的是哪张票。门禁住在 `v_invariant_checks_hardening` 里。

| # | 不变量 |
|---|---|
| 93 | 走到终态（succeeded / failed）的退款单必须经过放行（放行时间与放行人都要在） |
| 94 | 票码不许是券号派生的（券号是连号的，票码必须不可猜） |

- 退款绕过放行（不变量 93）—— 退款有三步：发起（requested）→ 放行（approved）
  → 落结果（succeeded / failed）。以前完成退款只拦终态，
  一笔 `requested` 的退款能被直接结掉 —— **放行这一步形同虚设**，
  审批形同不存在，钱却真的退了。现在 `fn_complete_refund` 只接受已放行的退款单。
- 票码可猜（不变量 94）—— 源侧没给票码时，我们以前拿券号（`VC` + 日期 + 序列）
  当票码。券号是连号的，**猜得到**；票码是闸机认的东西，猜得到就等于没有闸机。
  现在自己生成 128 位随机码，券号留作内部标识（对外展示、对账都用券号）。

### 5.12 组合映射口径（2026-11-07 落地）

到 011 为止，我们只处理了异构融合的**一个方向**（方向 A：一个源 SKU 覆盖多个我们的可售单元）。
但真实报文里还有另一个方向：

> **方向 B**：一个我们的可售单元，由多个源 SKU 按数量组成。

GlobalTix 官方示例的「家庭套餐」就是这一种：2 份成人门票 + 2 份成人快速通行证
+ 1 份儿童门票 + 1 份儿童快速通行证，源侧用**一条**映射表达式表达，
源侧一次预订就下完。我们原来的模型里没有「组合」这个概念，
于是这份报文只能被判成「当前模型表达不了的源侧结构」—— 报告里写着，但系统没法卖。

**这一段有六条口径，写在前面。**

第一，**两侧都要有声明，缺一不可**。规范侧声明组件与数量
（`product_variant_relation`：`quantity` = 组件要几份，012 新增的列），
源侧给配方（`supplier_variant_composition`：哪个源 SKU 顶哪个组件、订几份）。
只有一侧就是「我们说 2 大 1 小、源侧给 1 大 1 小」—— 不变量 80 挡住。

第二，**数量住在一处，两边都要有**。数量是套餐的本质（「2 大 1 小」的「2」是套餐的一部分，
不是一张成分表）。规范侧在 `product_variant_relation.quantity`，
源侧在 `supplier_variant_composition.quantity`，两边必须相等（不变量 79）。

第三，**配对关系记下来，不靠猜**。为什么单独记 `component_variant_id`：
两个组件数量一样、又被同一个源 SKU 覆盖得住的时候，猜就是瞎猜。
把「这个源 SKU 顶的是哪个组件」记下来，对账才是「源侧这一行 ↔ 规范侧那一行」逐行比。

第四，**覆盖判定只有一份**。能不能顶住某个组件，由库里的 `fn_variant_covered` 说了算
（Go 侧读法在 `internal/coverage`）。组合的要求 = 组件要求的并集
（`fn_variant_requirements`）—— 所以单个源 SKU 覆盖不住整张配方，
而整张配方（各成分覆盖的并集）覆盖得住。

第五，**组件暂时只有一层，不许嵌套**。组件要是组合，两侧的对账就得递归算，
错了没人说得清。结构上用触发器挡住（`fn_guard_included_relation`：
`included` 关系只许挂在 `combo` 变体上）。

第六，**组合暂不参与选源与定价，宁可少卖，不可卖错**。组合的成本 = Σ 组件成本 × 数量，
一次预订要带整组源 SKU —— 定价与预订还没接组合。
所以组合**不许直接挂源映射**（守卫触发器 `fn_guard_combo_mapping` + 不变量 81）：
挂上了，定价函数就会用**一个**源 SKU 的成本给整张套餐定价 —— 收三个人的钱，出一张票。

> 这一条在 §5.13 被兑现：组合现在参与定价与预订（成本按 Σ 成分成本 × 数量算，
> 预订按成分发），但「不许直接挂源映射」这条一个字没动 ——
> 组合的供给仍然只走配方。

> 第六条有个代价，说清楚：源侧把整套套餐当**一个** SKU 卖（方向 A 服务组合）的情况，
> 从 `coverage` 看不出来 —— 看得出的是「一个源 SKU 覆盖多个可售单元」，
> 不是「一个源 SKU 就是一整套」。
> zowoyoo 的 `ZWO-1D-BASE` 同时覆盖成人 / 儿童 / 老年，它不是家庭套餐。
> 看不出来就不能猜，所以这种形态单独声明（`supplier_variant_bundle`），
> 不推断。口径见 §5.15。

表与视图：

| 表 / 视图 | 干什么 |
|---|---|
| `supplier_variant_composition` | 组合映射的源侧配方：组合 ← 若干源 SKU × 数量 |
| `v_variant_composition` | 两侧并排：规范侧声明的组件与数量 ↔ 源侧的 SKU 与数量 |
| `v_invariant_checks_composition` | 组合映射侧不变量（78-81） |
| `v_invariant_checks_combo` | 组合售卖侧不变量（82-86） |

写路径的落点在 Go 侧的 `internal/compose`：把源侧的组合表达式解成配方、
核上规范侧的组件声明、核数量，写进 `supplier_variant_composition`（幂等，可重复执行）。
覆盖判定不在那里重写 —— 走 `internal/coverage` → 库里的 `fn_variant_covered`。
CLI 是 `tc-connect compose plan|apply`。

### 5.13 组合套餐的售卖口径（2026-11-07 落地，2026-11-08 修订第五条）

§5.12 的第六条说「组合暂不参与选源与定价，宁可少卖，不可卖错」。
这一段把那句话兑现了：组合现在**参与定价、参与下单、参与预订、参与出券、参与退款**，
但**仍然不许直接挂源映射**（守卫触发器 `fn_guard_combo_mapping` + 不变量 81 不变）。

**这一段有八条口径，写在前面。**

第一，**组合的成本 = Σ 成分单价 × 成分数量**，唯一实现是库里的
`fn_combo_components()`。定价（`fn_price_variant`）、下单（`fn_place_order`）、
排查（`v_combo_price_gap`）三处都从它取 —— 三处算三遍就是三个答案。

第二，**成分的源由配方定，不重新选源**。普通变体的采纳源由 `fn_route_candidates` 排序选出，
组合的成分由源侧配方（`supplier_variant_composition`）指定。理由是「选源与定价必须同源」
（硬约束 15）：配方里某个成分用的是 Zowoyoo，定价就必须按 Zowoyoo 的成本算，
不能按 Trip 的成本卖 Zowoyoo 的票。配方过期了要改配方，不是定价函数偷偷换源。

第三，**拿不准的一律不卖**，四种情形都表现为「当天不可售」，而不是拍一个价格出来：

| 情形 | 为什么不可售 |
|---|---|
| 某个成分当天没报价 / 成本折算不出来 | 组合的成本算不出来 |
| 成分不在同一个场次上 | 一次入园不是一个场次，包不起来 |
| 成分来自多个源 | 一次预订给不了两个源 |
| 组合走「按团报价」口径 | 团总价与成分份数不是一回事，口径还没定 |

缺口查 `v_combo_price_gap`（说得清差在哪：哪个成分、缺什么、多少钱）。

第四，**订单明细是一份套餐，成分行是履约的单位**。客户买的是**一份**套餐
（订单里一行明细），源侧要收两次单（成人 2 份、儿童 1 份），我们要发三张券。
所以新增 `sales_order_item_source`：一行 = 「这个明细要用哪个源 SKU、顶的是哪个可售单元、
要几份、能进几次场、成本多少、落在哪个场次」。普通变体也落一行（它自己），
所以履约只有一条代码路径。

第五，**预订按源 SKU 发，不按成分发**（2026-11-08 修订）。
最初的口径是「一条成分一条预订」（家庭套餐 = 2 条），那是错的：
参数化源里成人票与儿童票是**同一个源 SKU**（`ZWO-1D-BASE`，人群是购买时选的一档），
按成分建预订就是同一个源 SKU 在同一个源场次上订了两次。后果有三样：

- 源侧看到**两张订单单**（一次 2 张、一次 1 张），我们这边一条客户订单对两个源单号，
  对账时对不上；
- 退款要退两次，其中一次退不掉就是「钱退回来了但票还在」；
- 源侧只确认了其中一个成分时，整张套餐是半成品 —— 收了三个人的钱出了两张票。

所以预订的单位是**源 SKU**：源卖的是 SKU，我们就按 SKU 订。
成分的拆分留在预订的请求明细里（`request_payload.components`），
出券时再按成分把票码和持票人分下去。
幂等键是「订单号 + 明细 id + 源 SKU」，重跑不会重复下单，
也不会把同一个源 SKU 订第二次（唯一索引 `ux_booking_one_per_source_sku` 兜底，
不变量 87 / 88 复查）。

**代价说清楚**：成分可以来自不同的源商品（GlobalTix 的门票 + 快速通行证是两个源商品），
所以一张套餐有几条预订 = 有几个源 SKU。整张套餐的原子性（要么全出票、要么全退）
取决于源侧的能力，我们这边只保证「所有成分都出票了才算履约完成」。

一个源 SKU 把整套套餐当一个商品卖的情况，从 `coverage` 看不出来
（看得出的是「一个源 SKU 覆盖多个可售单元」，不是「一个源 SKU 就是一整套」），
所以这种形态单独声明，不推断 —— 口径见 §5.15。

第六，**出券与实名按成分**。2 份成人 + 1 份儿童 = 3 张券、3 份实名；
实名按成分变体分组收（成人的姓名证件、儿童的姓名生日）。
一个成分变体同时出现在多行明细里时（「一张家庭套餐 + 一张单买成人票」），
实名必须带 `item_index` 指明是哪一行 —— **分不清就不许猜**
（猜错是把甲的实名绑到乙的票上，闸机前才发现）。

第七，**超卖按场次加总**。两个成分可能抢同一个源票种（参数化源：
一个人群参数化的 SKU 同时顶成人/儿童），那就是**同一个池子**。
逐成分各查各的会各查一遍池子、加起来超卖 —— 所以下单时除了逐成分查，
还要按源场次把这一单的需求加总，跟这个场次的总可售数比一次。

第八，**退款是整单退，事实一起改**。三张券全部作废、预订全部取消
（家庭套餐 = 一条预订，因为两个成分共用一个源 SKU）、两条预占全部收回
（`voided`：卖过又收回，兑现量仍是原数 —— 事实不许被改写）。

表与视图：

| 表 / 视图 | 干什么 |
|---|---|
| `sales_order_item_source` | 订单明细的成分行：履约的单位（出券 / 预占 / 实名都按它走；预订按源 SKU 建，成分由 `fn_booking_components` 推出来） |
| `fn_combo_components()` | 组合成分的唯一实现：一行一个成分（配方 + 当天报价 + 折算 + 场次） |
| `fn_booking_components()` | 一条预订覆盖哪些成分的唯一读法：按「明细 + 源 SKU + 源场次」推出来 |
| `fn_bound_supplier_session()` | 场次级绑定的唯一实现：规范场次 + 源商品 → 源场次 |
| `v_order_item_source` | 成分对账：每行成分的源、数量、成本、份数、订了没有、发了几张券 |
| `v_combo_price_gap` | 组合当天为什么不可售：差在哪、缺什么、多少钱 |
| `v_invariant_checks_combo` | 组合售卖侧不变量（82-88） |

**这一段还改了一处 009 的口径**：`fn_available_qty` 的池子归属。
源侧只报场次合计（票种为空的快照行）时，那个池子是**全票种共享**的，
所以算「我们的承诺」时要算整个场次的承诺，不能只算本票种的 ——
不然每个票种都能把整场次的可用量再花一遍（卖 2 张成人再卖 2 张儿童，池子里只有 2 张）。
票种级快照没有这个问题（每个源票种一个池子，互不相干）。

**这一段暂时没做的**：C 端读模型（`c_variant_calendar` / `c_product_card`）仍然只认
`price_calendar`，而组合没有自己的 `price_calendar` 行 —— 组合今天只能从 B 端分销链路下单，
还上不了 C 端日历。原因是组合的「有效期终点」和「人群标签」还没有定：
2 份一日成人票 + 1 份一日儿童票的组合，有效期是 1 天还是 2 天？
人群标签是「家庭」还是「成人+儿童」？这两件事定了再进读模型，
否则前端会自己加一天、自己猜人群 —— 那是 010/011 刚根治掉的 bug。

（这两件事在 §5.14 定了，缺口已闭合。）

### 5.14 组合在 C 端的落地口径（2026-11-08 落地）

组合是**我们自己的配方** —— 源侧没有对应的商品条目，
目录同步作业看不见它。所以 §5.11 的读模型纪律对它不自动成立：
源侧同步跑得再勤，组合在 C 端也是一片空白。
015 把这条路径补上：**组合的售价行与日历格子由它自己的配方推出来。**

**这一段有七条口径，写在前面。**

第一，**组合的售价行由成分的售价行推出来**。`fn_sync_combo_calendar()` 取成分在
同一天、同一源场次上的售价行，凑齐全部成分才算这个组合当天可售，
金额仍走定价函数的组合分支（成本 = Σ 成分单价 × 份数）——
不许在同步作业里另算一遍钱。

第二，**有效期终点 = 成分窗口的并集**（`fn_variant_validity_days` 的组合分支取最长）。
2 份一日成人 + 1 份一日儿童 = 1 天；2 份两日成人 + 1 份一日儿童 = **2 天**。
不是最短（第二天进不去），也不是和（多赔客户一天）——
不变量 89 拿两边独立读的值比，口径写错当场红。

第三，**人群是编码，不是标签**。组合不带一个「家庭」标签；
它带的是每个成分的**人群编码 + 份数 + 各自管几天**（`adult × 2` / `child × 1`）。
「2 成人 + 1 儿童」这句话由前端按 locale 拼 —— 展示文案不进模型（硬约束 9）。

第四，**构成是结构化事实，进读模型**。`c_variant_composition` 一行一个成分，
`v_c_variant_composition` 供详情页直接读。请求链路不许 join 主数据去算份数。
读模型是**按渠道**建的：同一个套餐上了两个渠道就有两份成分明细，
所以成分明细必须**按渠道读** —— 不按渠道过滤，
「2 份成人 + 1 份儿童」会被数成两遍，详情页显示 4 份成人、实际只发 2 份。

第五，**读模型不许与主数据分叉**（不变量 90）。多一行、少一行、
份数从 2 变成 5、天数变了，都算分叉 —— C 端会显示「5 份成人」，实际只发 2 份。

第六，**挂着的组合必须卖得掉**（不变量 91）。日历格子上必须有价格；
卖不了的套餐不许占一个位置。

第七，**组合没有单一源币种，折算留痕在成分上**。一张套餐的成本是
Σ 成分成本 × 份数，成分可能各自是不同币种（源侧日元、我们卖人民币）。
所以组合售价行的顶层 `fx_rate` / `fx_as_of` 是**空的** ——
那是「这里没有单一的值」，不是「同币种、汇率 1」；
填成 1 是声称「没折算过」，那会让对账去查一份不存在的折算。
逐成分的留痕在 `price_calendar.rule->'combo'` 里：
同币种 → 因子 1、快照日期为空；跨币种 → 必须有快照日期，
且因子能用这个日期独立复算出来（不变量 92）。
这条路径以前没人复查：组合的 `cost_source_product_id` 是空的，
不变量 45 按这个字段 join 源价行，直接跳过组合。
